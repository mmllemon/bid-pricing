# 投标报价利润最大化系统：代码审查与需求基线

版本：v0.1.0 发布基线  
日期：2026-09-20

## 1. 审查结论

当前仓库已经具备一个可验证的报价计算内核：

- 已有 Excel 读取、清洗、匹配、约束建模、Phase 1 解析求解和 Phase 2 LP 求解链路；
- 当前真实项目 81 个清单的 Phase 1/Phase 2 对拍已通过；
- 测试体系覆盖输入、规则、求解、复核、审计等模块，最近一次完整状态为 1393 项通过；
- 现有输出可生成报价明细 Excel。

但它还不是正式用户软件。当前最大风险不是“数学模型不能跑”，而是“用户上传的真实 Excel 口径没有被完整、显式地锁定”。在进入正式界面开发前，应先完成以下 P0 口径修正。

## 2. 必须修正的 P0 问题

### 2.0 固定成本与最优报价的关系

如果业务费、公司管理费等确实是与各清单报价无关的项目固定成本，那么它们不进入单项 `c_i` 时，通常不会改变“竞争性清单之间如何分配既定竞争预算”的最优解；它们会减少最终利润，并且如果计入总报价分解，还会减少可分配的竞争部分预算。

这个结论有一个前提：固定成本不能随着某一项工程量、单价或方案变化。如果它实际上按产值、人工费或某些清单比例变化，就不能当作固定成本，必须分摊进相关 `c_i`。

### 2.0.1 不平衡报价条款漏洞

现有仓库虽然已经定义了 C13，但旧的主报价流程没有把 C13 接到 `run_quote_pipeline`，因此在存在不平衡报价条款时可能仍产生 0.01 元报价。这是业务缺陷，不是单纯提示问题。

本轮已增加 `src/bidpricing/validation/unbalanced.py` 和回归测试：

- `BID_VALIDITY + CAP`：按 `cap × (1 - tol_lo)` 提高单项最低报价；
- `SETTLEMENT_ADJUSTMENT`：在结算调整公式尚未接入前直接阻断；
- 无最高限价项：不把空值当 0，但提示“C13=CAP 无法计算条款下界”；
- 未声明条款：保留警告，正式产品入口应要求用户明确选择“有/无”。

因此，0.01 元报价只有在招标文件没有相应不平衡报价限制、且其他约束允许时才可能作为数学结果；不能直接视为可提交报价。

### 2.1 成本税口径冲突

当前 `config/basis_declarations.json` 将成本单价声明为 `EXCL_VAT`，`cost_basis_spec.json` 也按成本与报价同为不含增值税设计；这与最新业务要求冲突：

> 限价清单综合单价 = 不含税最高限价；成本清单综合单价 = 含税成本单价。

不能把含税成本直接与不含税报价比较。系统必须新增以下明确字段：

```text
cap_unit_price_tax_scope = EXCL_VAT
cost_unit_price_tax_scope = INCL_VAT
cost_input_vat_rate = 用户填写/成本清单项目口径
input_vat_credit_mode = FULL / PARTIAL / NONE / UNKNOWN
```

只有在“进项税可足额抵扣、税率明确、成本单价确实含税”的条件同时满足时，才可以计算：

```text
c_i_excl_vat = c_i_incl_vat / (1 + cost_input_vat_rate)
```

若进项税不能抵扣或抵扣比例未知，不能擅自除税，应使用有效成本：

```text
c_i_effective = c_i_incl_vat - 可确认抵扣的进项税
```

缺少上述声明时，系统应显示“成本税口径未定”，禁止输出“最优利润”结论，只能输出数据校验结果。

### 2.2 空白限价的处理

业务规则：限价清单“综合单价”为空，表示该项没有最高限价，由用户自行报价，只需备注提示。

现有底层数据结构已经支持 `cap=None / no_cap=true`，这是正确方向；但正式产品还必须做到：

1. 导入时识别为空值，而不是识别成 0；
2. 不把该项当成异常缺失；
3. 允许其进入报价优化；
4. 在结果表增加“无最高限价”标识和备注；
5. 仍受总报价预算、单价最小分辨率和其他启用约束的隐含限制；
6. 若没有任何可推导上界，必须阻断求解，而不是使用任意大数。

### 2.3 固定格式 Excel 必须有“模板适配层”

当前解析器已有列别名和表号识别，但正式上传流程还缺少：

- 固定模板版本识别；
- 限价清单与成本清单的来源侧校验；
- 表头、工作表、字段类型、重复编码的用户友好提示；
- “空值/缺列/缺行/零值/格式错误”的区别展示；
- 导入前预览和确认。

正式界面不能直接把用户文件交给求解器，必须经过：

```text
上传 → 模板识别 → 字段映射 → 数值清洗 → 两侧匹配 → 异常确认 → 口径确认 → 求解
```

### 2.4 隐形成本必须显式建模

业务费、公司管理费、融资费、项目部管理费、风险储备等隐形成本会影响最优利润。如果不纳入成本，系统会高估利润；如果全部重复摊入每个清单，又会低估利润。

必须把隐形成本分为三类：

| 类型 | 处理方式 | 是否影响单项最优分配 |
|---|---|---|
| 可直接归属某清单 | 加入该清单的有效成本 `c_i` | 影响 |
| 可按规则分摊到清单 | 按明确基数和费率分摊进 `c_i` | 影响 |
| 项目整体固定费用 | 进入固定税前费用或单独固定成本项 | 影响总利润，但不改变清单间排序 |

最低需要用户填写：

```text
cost_components:
  labor
  material
  equipment
  subcontract
  project_management
  corporate_overhead
  business_expense
  financing_cost
  risk_reserve
  other
allocation_basis: DIRECT / LABOR / DIRECT_COST / OUTPUT / FIXED_PROJECT
allocation_rate: 数值
```

所有未计入的费用必须在结果中明确列为“未纳入成本的风险”，不能默认为 0 后不提示。

## 3. 当前代码架构评价

### 3.1 已做得比较好的地方

1. `io → matching → solver → verifier → output` 分层清楚；
2. Phase 1 与 Phase 2 分离，且已经完成真实项目对拍；
3. `cap=None` 与缺行、空值、0 值有区分意识；
4. 配置文件承担规则来源，避免大量业务规则散落在代码中；
5. 大量测试覆盖异常、阻断、精度和状态转换；
6. 求解后有独立约束复核，不只相信求解器状态。

### 3.2 需要优化的地方

#### A. 生产入口不完整

目前主要能力通过模块和 CLI 检查命令暴露，没有一个面向用户的完整 `upload → calculate → export` 入口。应新增应用服务层，不让界面直接调用求解器内部对象。

#### B. 业务口径和技术字段还没有完全分离

`c_i` 目前同时承担“输入成本单价”和“求解使用成本”两个含义。应拆分为：

```text
cost_unit_price_input
cost_tax_scope
cost_unit_price_effective
cost_adjustment_trace
```

#### C. 无最高限价的用户提示还没有贯穿输出层

底层可表达无上限，但 Excel 和界面必须展示“无最高限价，自主报价”，并将其计入风险/提示统计。

#### D. 隐形成本没有正式的数据模型

当前成本证明规范已有管理费、分摊费用和风险储备的概念，但还没有把业务费、融资费、公司管理费作为上传/录入/分摊的完整输入协议。

#### E. 错误信息需要面向用户重写

底层的 `BLOCKED/FAIL/WARN` 适合审计，不适合界面。需要同时输出：

```text
机器状态：BLOCKED
用户提示：成本清单为含税单价，但尚未填写进项税抵扣方式，暂不能计算最优利润。
处理建议：填写税率和抵扣方式，或将成本口径改为不含税。
```

#### F. 配置变更缺少版本化的项目快照入口

一次报价应保存：两份原始 Excel 哈希、解析结果、口径声明、参数、求解器版本、结果和人工确认记录，保证可以一键复算。

## 4. 正式产品的目标边界

### 输入

- 固定格式限价清单 Excel；
- 固定格式成本清单 Excel；
- 用户总报价；
- 措施费、规费、税率；
- 成本税口径和进项税抵扣方式；
- 隐形成本及分摊方式；
- 可选报价约束和方案参数。

### 输出

- 分部分项最优综合单价；
- 清单合价、成本、利润、利润率；
- 无最高限价项目提示；
- 缺成本、缺工程量、编码不匹配、重复项等异常清单；
- 多方案对比；
- Excel 报价成果；
- 可复算的项目快照和计算日志。

### 明确不承担的职责

- 不自动判断投标是否一定合规；
- 不自动猜测成本清单和限价清单的税口径；
- 不自动把缺失成本或隐形成本填成 0；
- 不把没有上限的清单强行套用其他清单的限价。
