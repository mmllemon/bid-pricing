# 投标报价平台：后续迭代与维护策略（深度论证）

版本锚点：`v0.1.0`（2026-09-20）  
文档性质：**规划文档**，不是状态快照（那是 `STATE.md`），也不是接手手册（那是 `PROJECT_HANDOFF.md`）。  
本文回答三个问题：**接下来做什么**（迭代路线）、**怎么做才安全**（维护/迭代纪律）、**新东西怎么进来**（模块接入规范）。

> 本文不修改版本号、不打 tag。落地执行仍遵循「判据先于实现、证据先行、STATE.md 复算生成」。

## 0. 结论速览

| 优先级 | 事项 | 一句话论证 |
|---|---|---|
| P0 | 成本税口径闭环 | 当前成本按含税处理、报价按不含税比较，**口径混用会让利润结论失真**，这是正确性红线 |
| P0 | 模板适配层 | 平台要面向真实造价人员，**换文件即失败的解析器不能算可用产品** |
| P0 | CI 门禁自动化 | 1393 项测试跑一次 32s，**不接 CI 等于每次交付都靠人记得跑** |
| P1 | 隐形成本录入与分摊 | 固定成本不进单项 `c_i` 会高估可分配利润；不建模就无法回答「报价是否留足费用」 |
| P1 | 项目台账 / 结算管理 | 业务上高频、技术上是现有模块（overview/settlement）的**自然延伸**，风险最低 |
| P2 | 多用户权限 / 协作 | 当前无登录、无鉴权；多人共用一台机才需要，**过早做是浪费** |
| 持续 | 仓库结构清理 | 旧 streamlit 入口、build 脚本重复、前端单文件膨胀，**不清理会随功能增长恶化** |

维护与迭代的三条铁律：

1. **STATE.md 永远是复算产物**——改完代码必须 `status --write` 再对账，不手写数字。
2. **任何新字段 = 五处同步**（配置 + 内核 + API + 前端/Excel + 测试/文档），缺一即漂移。
3. **不可逆决策必须写 ADR**——聊天记录不承载结论。

## 1. 现状盘点（论证的起点）

### 1.1 已确立的三层架构

```text
网页平台（FastAPI 8000 + 原生 JS 8080）
   │  薄入口，不碰求解器内部对象
业务层（src/bidpricing/*.py，纯 Python 可单测）
   ├─ io/            读取、清洗、匹配、导入登记
   ├─ validation/    缺失、成本、利润、C13、不平衡、低价、隐形成本
   ├─ solver/        Phase 0/1/2、编译器、后端、复核、诊断、稳定性
   ├─ contracts/     2013/2024 规则集与选择
   └─ 应用模块        quote_pipeline / settlement / project_store / plan_compare / deployment
质量设施（config/ 制品 + tests/ + docs/adr/ + docs/STATE.md + docs/tasks.json）
```

这套结构的优点：**判据与实现分离**（judge_* 只吃原始量）、**独立复算路径**（refimpl 不 import 生产模块）、**制品冻结**（hash/version/frozen_at）。这些是本项目防「静默错误」的三道防线，后续任何迭代**不得削弱**。

### 1.2 当前质量基线

- 全量测试 **1393 项通过**（`python -m unittest discover -s tests -t .`，约 32s）。
- `contract-check` 跨制品一致性、Gate 0a/0b/Phase 0 机械判据、`extract_tasks --check` 任务板漂移校验均已绿。
- ADR 决策记录 34 项；`docs/tasks.json` 68 项任务，遗留 9 项（T04-04 奇偶校验、T07-03 精度监控、T07-04 参数校准等）。

### 1.3 已知缺口（迭代的靶子）

1. **成本税口径**（[CODE_REVIEW_AND_REQUIREMENTS.md §2.1](file:///d:/Lee-proj/TRAE/bid-pricing-build/bid-pricing/docs/CODE_REVIEW_AND_REQUIREMENTS.md)）：成本清单综合单价 = 含税成本，限价 = 不含税最高限价。缺少进项税抵扣声明时，模型利润 ≠ 财务利润。
2. **隐形成本**（§2.4）：业务费/管理费/融资费/风险储备未完整建模，不填即高估利润。
3. **模板适配层**（§2.3）：解析器有列别名与表号识别，但缺模板版本识别、友好错误、导入前预览确认。
4. **空白限价 / 无上限项**：已识别提示，但不能自动优化，结果转人工。

这些缺口全部来自「把用户真实口径显式锁死」这一原则，迭代必须继续贯彻，**不能为了功能丰富度而跳过口径确认**。

## 2. 后续迭代建议（按价值排序 + 深度论证）

### 2.1 P0：成本税口径闭环（正确性红线）

**现状**：`cost_basis_spec.json` 已声明成本含税、进项抵扣方式存在 `input_vat_credit_mode` 概念，但有效成本转换链路未闭环；缺声明时没有系统性阻断「最优利润」结论。

**论证**：
- 为什么是 P0：**模型输出的利润数字若基于错误口径，比没有输出更危险**——用户会拿它去投标决策。
- 为什么现在做：缺口已经明确、方案已在 CODE_REVIEW 文档论证（`c_i_excl_vat = c_i_incl_vat / (1+rate)`，抵扣不明时用 `c_i_effective`），实现路径清晰。
- 风险：改成本口径会影响既有求解结果——必须配「老结果在新口径下复算不一致」的回归，不能只测新代码。

**验收判据**：无抵扣声明时状态为「成本税口径未定」并禁止输出利润结论；声明 FULL + 税率后输出可复算的 `c_i_effective` 且与手工计算一致。

**接入点**：`validation/cost_basis.py` + `quote_pipeline.py` + 前端参数表单 + `project_quote_policy.json`。

### 2.2 P0：模板适配层（从「能解析」到「能用」）

**现状**：解析器靠「表号 + 别名集合」双键识别，能处理真实文件；但模板版本识别、字段映射预览、`空值/缺列/缺行/零值/格式错误` 的差异展示、导入前确认，都还没有。

**论证**：
- 业务价值：造价人员上传的文件千差万别，**解析失败时的报错质量直接决定产品口碑**。现在失败大概率是「解析失败」四个字，用户无法自助修复。
- 技术风险：低。不动求解内核，只扩 `io/` 层与 `import_preview.py`。
- 成本：中等。需要维护「模板版本 → 列映射」注册表，并把它接入预览前端。

**验收判据**：对已知失败样本（缺列、错表头、重复编码、格式错误）分别给出可读的中文错误与修复建议；导入前预览展示行数/字段/覆盖/异常/哈希（H-006 已具备，补「确认后进求解」一步）。

**接入点**：`io/boq.py` + `io/xlsx.py` + `import_preview.py` + 前端上传页。

### 2.3 P0：CI 门禁自动化

**现状**：交付前手动跑 `unittest + contract-check + status --write`；仓库已推到 GitHub 私有仓库，但没有任何自动化。

**论证**：
- 为什么值得：1393 项测试 32s，**每次交付都靠人记得跑，等于把质量门禁寄托在记忆上**——与本项目「记录成本从人转移到工具」的治理哲学（GOVERNANCE）直接冲突。
- 怎么做：GitHub Actions 一个 workflow 即可，双环境（零第三方依赖 + 装 PuLP/HiGHS）各跑一遍，`status --write` 后 diff 校验快照是否与代码一致。
- 收益：任何提交都自动验证「测试全绿 + 契约一致 + 快照未漂移」，接手者不再需要手工复算才能放心。

**验收判据**：推送后 Actions 自动跑绿；故意改坏一处契约时 PR 标红。

**注意**：CI 里不要跑 `freeze --all`（会改制品 hash），只跑校验与复算。

### 2.4 P1：隐形成本录入与分摊

**论证**：
- 业务价值：投标报价必须覆盖业务费、公司管理费、融资费、项目部管理费、风险储备。不建模 → 高估可分配利润 → 报出来的价「看起来赚、实际亏」。
- 设计红线（来自 CODE_REVIEW §2.4）：三类分法——可直接归属清单的进 `c_i`；可按规则分摊的按明确基数和费率摊；项目整体固定费用进固定税前费用。**不得重复摊、不得默认 0 后不提示**。
- 风险：分摊基数的选择（DIRECT/LABOR/DIRECT_COST/OUTPUT/FIXED_PROJECT）是业务决策，必须做成显式参数而不是代码假设。

**验收判据**：三类成本各自可录入、可追溯、进入结果明细；未计入的费用在结果中列明为「未纳入成本的风险」。

**接入点**：`validation/hidden_cost.py`（已有骨架）+ 前端参数区 + 结果表扩展列（**扩展列必须同步 api/app.py、frontend/app.js、build_web_result.mjs、测试与本文档**）。

### 2.5 P1：项目台账 / 结算管理模块

**论证**：
- 现状：工作台已有经营概览看板（投标/中标在建/完工/结算/售后）与 `settlement.py` 结算规则引擎（2013/2024）。
- 延伸路径：把「结算期工程量实际值 Q1」录入能力接入——报价期用 `q1` 预估，结算期用实际值回算 `settlement_amount`，形成**报价 → 结算的闭环对账**。这是本系统相对普通报价工具最有差异化的能力。
- 风险：低。复用既有 settlement 引擎，新增的是数据录入与展示。

**验收判据**：项目从投标阶段流转到结算后，可录入实际工程量并回算结算金额，与报价预测的偏差可视化。

**接入点**：`project_overview.py` + `settlement.py` + 工作台结算列。

### 2.6 P2：多用户权限与协作

**论证**：当前已有多用户目录隔离（`outputs/<projects|web-results>/<用户>/`），但**无登录、无鉴权**——隔离是路径隔离，不是权限隔离。多人共用一台机或部署到服务器才需要真实鉴权。在个人单机使用阶段做完整 RBAC 属于过度设计；建议在部署到共享环境前只做「访问日志 + 用户切换」增强。

**验收判据**：部署到局域网后，他人无法通过改用户名目录看到他人数据（等鉴权真正立项时再定细节）。

### 2.7 其余候选（小步快跑型）

| 候选 | 价值 | 成本 | 说明 |
|---|---|---|---|
| 方案模板库 | 中 | 低 | 常用参数组合存为模板，减少重复录入 |
| 报价历史对比时间线 | 中 | 低 | 同一项目多次报价的演进视图 |
| 批量导入/导出 CSV | 中 | 低 | 造价人员习惯 Excel 批量操作 |
| 风险清单自动生成 | 中 | 中 | 基于缺成本/无上限/低比率项自动产出风险提示 |
| 投标预警（开标日期提醒） | 低 | 低 | 工作台已有日期胶囊，顺带做 |

## 3. 安全高效维护的策略

### 3.1 六层记录体系是地基（不重建，只遵守）

GOVERNANCE.md 已定义 L1 事实 → L6 交接 的六层记录体系。维护者的义务不是增加层，而是**遵守每层的写入者与更新时机**：

| 层 | 什么时候碰 | 禁止 |
|---|---|---|
| L1 事实（config/src） | 开发时改 | 文档里写与代码不一致的口径 |
| L2 意图（tasks.json） | 任务完成时 | 手改结构字段（用 `extract_tasks.py`） |
| L3 决策（ADR） | 做不可逆决策时 | 改写已定稿 ADR（追加式，推翻用新 ADR） |
| L4 变更（CHANGELOG/tag） | 达里程碑时 | 逐次提交都写 CHANGELOG |
| L5 快照（STATE.md） | 脚本生成 | 手写任何数字 |
| L6 交接（memory 日志） | 每次会话结束 | 把交接当权威结论 |

### 3.2 契约同步清单（防漂移的第一道闸）

项目多次事故的根因都是「一处改了、另一处没改」。维护中凡是**新增或修改一个业务字段**，必须走这张清单：

1. `config/` 制品（字段声明、默认值、范围、枚举）
2. 内核实现（`src/bidpricing/` 对应模块）
3. API 层（`api/app.py`：表单字段、响应字段）
4. 前端（`frontend/app.js` + 样式；用户输入过 `esc()`）
5. Excel 导出（`build_web_result.mjs`：列、格式、列名）
6. 测试（新增字段的正反用例）
7. 文档（本文档级：PROJECT_HANDOFF / USER_PRODUCT_SPEC / 输出契约）

漏一项 = 产生一处静默漂移。**验收判据**：`contract-check` 与全量测试全绿，且手工核对前端展示与后端返回一致。

### 3.3 状态快照纪律

- 改任何 `src/`、`config/`、`docs/tasks.json` 后，交付前必须 `python -m bidpricing.cli status --write`。
- 快照里的测试数字、闸门状态、任务状态都是 `collect()` 复算的，**不得手改**。
- 若复算结果与旧快照不一致：以复算为准，先搞清楚「是代码变了还是快照过期了」再提交。

### 3.4 清理纪律（删东西前先查证据）

- `docs/tasks.json` 的 `evidence` 会引用文件路径（如 `tests/data/t06-01/报价表.xlsx`）。**删除任何被证据引用的文件会导致测试失败**（T06-01 曾踩过：清理 outputs 后测试红）。
- 删除前：`grep` 仓库内所有引用（代码、测试、docs、config），确认无引用再删。
- 运行时产物（`outputs/`、`docs/parsed/`、`node_modules/`、`*.log`）一律 gitignore，不进版本库。

### 3.5 前端缓存与命名纪律

- 修改 `app.js` / `styles.css` / `workbench.js` / `workbench.css` 后**必须递增版本查询串**（如 `wb31` → `wb32`），否则浏览器 HTML 缓存会加载旧脚本（曾造成「下拉显示旧值」假象）。
- 方案 JSON 命名 `<报价金额>_<id>.json`、Excel 命名 `<项目名称>-<报价金额>.xlsx` 是**文件名契约**，改命名必须同步 `project_store.py` 与 `_excel_filename`。
- 金额一律 2 位小数（元）；报价比率列百分比格式 `0.0%`、金额列 `#,##0.00`。

### 3.6 用户隔离纪律

`outputs/<projects|web-results>/<用户>/` 的默认目录**必须在调用时解析**，不得在模块定义时绑定（`project_store.PROJECTS_DIR` 曾因此失效）。

## 4. 安全高效迭代的流程

### 4.1 分支与提交

- 个人项目建议 **master 直推 + 小步提交**（每次提交只解决一件事，中文 conventional 前缀：`feat/`、`fix/`、`chore/`、`docs/`、`test/`）。
- 一次提交 = 一个可独立验证的单元：改代码 + 改测试 + 改文档同步进**同一个**提交，避免「代码先行、文档永远落后」。
- 里程碑达 tag（`vX.Y.Z` 或 `<主题>-v<N>`）时同步 CHANGELOG。

### 4.2 测试先行与独立复算

- **判据先于实现**：先写 `judge_*` 判据与测试（注入错误实现必须 FAIL），再写正确实现。
- **求解器结果必须独立复算**：Phase 2 MILP 目标值不是最终可信利润，必须有独立路径核对（`refimpl` 不 import 生产模块）。新增任何求解逻辑都要挂 `verify-solution`。
- 新增判据**双向验证**：注入错解必 FAIL、正确解必 PASS；「判据覆盖不到的情形」至少 WARN 而不是静默 PASS。

### 4.3 门禁清单（每次交付前必跑）

```powershell
# 1. 工作区干净检查
git status --short

# 2. 全量测试
$env:PYTHONPATH="src"; python -m unittest discover -s tests -t . -q

# 3. 契约一致性（跨制品）
$env:PYTHONPATH="src"; python -m bidpricing.cli contract-check

# 4. 任务板漂移校验（如改过 tasks.json 或 extract_tasks.py）
python tools/extract_tasks.py --check

# 5. 重新生成状态快照（并 diff 确认无意外变化）
$env:PYTHONPATH="src"; python -m bidpricing.cli status --write
git diff --stat docs/STATE.md
```

### 4.4 版本与发布

- 语义化版本：破坏性变更 → minor bump；修复/小功能 → patch；重大架构 → major。
- 每次 bump 同步：CHANGELOG 里程碑 + git tag（annotated，带说明）+ STATE.md 重新生成。
- 发布前过一遍 §4.3 门禁清单。

## 5. 新功能模块接入规范（五步接入法）

新模块（如「结算管理」「风险清单」）按以下五步接入，**顺序不可颠倒**——第 1 步不做，后面都是空中楼阁：

### 第一步：制品先行

- 在 `config/` 新建或扩展规范 JSON（字段、判据、枚举、容差、消费者）。
- 字段必须声明 `type/required/default/min/max/enum/description`；阈值必须具名（禁止裸数字）。
- 走 `freeze` 冻结（写入 version/hash/frozen_at）。**没有冻结制品的模块不接进主流程。**

### 第二步：内核实现（纯 Python，判据与实现分离）

- 在 `src/bidpricing/` 下新建模块：计算函数 + `judge_*` 判定器 + 报告函数。
- `judge_*` 只吃原始量（不消费 `SolveResult` 等内层结论），保证判定可注入验证。
- 该模块**不得 import 任何求解器包**；求解能力一律走 `solver/backend.py` 适配层。

### 第三步：独立验证

- 新逻辑能独立复算的，必须给独立路径（参考实现或数值对拍），不能只信求解器自报。
- 新增 CLI 子命令（`bidpricing <module>-check`）与 `tests/test_<module>.py`（判据双向验证）。
- 真实项目样本能挂上的挂上（如 xiyong_l_district），验证「不是玩具数据才通过」。

### 第四步：API 与前端接线

- `api/app.py` 加薄端点（只做参数收解、调用内核、序列化，不做业务决策）。
- 前端：新页面或新组件进对应视图；**用户输入一律 `esc()` 转义**；数值列右对齐 + `tabular-nums`。
- 修改前端文件后递增版本查询串；下拉用 `cs-label` 自定义样式；模态追加到 `#workbenchView` 而非 `document.body`。
- 若产生新 Excel 列，同步 `build_web_result.mjs` 与命名契约。

### 第五步：证据闭环

## 7. 风险与权衡（红线清单）

迭代中**不得触碰**的红线（每条都有事故或论证背书）：

1. **不削弱三层独立性**：refimpl 一旦 import 生产模块，独立复算即失效（ADR-0027）。
2. **不把 STATE.md 当事实源**：它是生成物；事实源是代码、配置与现场复算。
3. **不改清单原始顺序**：任何重排都是回归（用户偏好 + 输出契约）。
4. **不静默补缺**：空限价 ≠ 0、缺成本不代填、空值 ≠ 缺行；补缺必须有显式确认。
5. **低价确认 ≠ 废标判定**：只留痕不判决；所有结果附「是否废标以招标文件为准」。
6. **不引前端框架**：保持原生 JS 轻量（硬约束，勿因新模块破例）。
7. **不把聊天记录当结论**：条款解释必须落配置/ADR。
8. **重复键必须显式阻断**：`p_by_id` 假设 item_id 唯一，冲突编码不能静默覆盖。

**权衡原则**：功能丰富度 < 口径正确性；开发速度 < 可复算性。任何「先上线再补」的口径都必须先建「缺声明即阻断」的闸门。
