# 项目说明：bid-pricing 是什么、怎么用、现状如何

> 本文件由 `docs/PROJECT_HANDOFF.md`、`docs/USER_PRODUCT_SPEC.md`、
> `docs/PRODUCT_ROADMAP_AND_TASK_PLAN.md` 三份入口文档合并而成（2026-10-07）。
> 旧文件已删除，内容以 git 历史为准。
> 状态数字一律以自动生成的 [`STATE.md`](STATE.md) 为准，本文件不写数字。

## 1. 一句话

给定总报价，联合求解分部分项综合单价，使结算调整后利润最大，输出可复核的 Excel。

用户提供：限价清单 Excel（不含税最高限价）、成本清单 Excel（含税成本单价）、
目标总报价、固定税前金额、税率、招标文件的不平衡报价条款与报价区间。
系统在总报价固定、限价不超限、报价区间等约束下求解各清单综合单价。

## 2. 用户操作流程

```text
新建项目
  ↓
上传限价清单 Excel + 成本清单 Excel
  ↓
系统识别模板并预览字段（行数/字段/匹配覆盖/异常/文件哈希）
  ↓
确认税口径、进项税抵扣方式、固定费用和隐形成本
  ↓
查看异常并处理/确认（BLOCKED 必须处理，WARN 可确认继续，INFO 只提示）
  ↓
输入总报价 → 点击"计算最优报价"
  ↓
查看方案结果 → 修改参数/复制方案/重新计算
  ↓
导出报价 Excel 和计算说明
```

低价确认 ≠ 废标判定：报价比率低于阈值时只做确认留痕（用户/时间/条款依据），
结果恒附「是否废标以招标文件为准」。

## 3. 已确认的业务口径

| 事项 | 当前口径 |
|---|---|
| 限价综合单价 | 不含税最高限价 `cap_excl_vat` |
| 成本综合单价 | 含税成本 `cost_input_incl_vat` 入账，产出毛利前换算为不含税有效成本 `cost_effective`；声明缺失即阻断（H-002 / ADR-0035） |
| 单项报价是否必须高于成本 | 不必须；允许单项毛利为负 |
| 措施项目费、规费 | 按当前固定税前金额处理 |
| C13 基准 / 低价阈值 | 最高限价；报价比率 <50% 需确认留痕 |
| C13 工程量阈值 | 相对限价工程量偏差超 ±15% 触发结算调整 |
| 空白限价 | `no_cap=true`，识别并提示，结果转人工报价（空 ≠ 零） |
| 清单顺序 | 保留原限价清单顺序；成本侧独有项按成本输入顺序插入 |
| 项目凭证 | `project_id` 只存经营概览真实项目 UUID；`project_name` 承载展示名/目录名 |
| 输出语言 / UI 风格 | 中文；简洁浅色，业务清晰度优先 |

模型利润 ≠ 最终财务利润：项目固定成本与隐性成本链路未闭环。

## 4. 数据模型（核心字段）

```text
QuoteItem
  project_id / unit_work / item_id          复合主键（重复键阻断，不合并）
  q0 / q1_point                             限价工程量 / 成本清单工程量
  cap_excl_vat                              不含税最高限价（空 = 无最高限价）
  cost_input_incl_vat / cost_effective      含税成本 / 换算后有效成本
  no_cap / cost_missing / provenance

QuotePolicy
  target_total / fixed_pretax / vat_rate / surtax_rate
  cap_tax_scope = EXCL_VAT / cost_tax_scope = INCL_VAT
  cost_input_vat_rate / input_vat_credit_mode
  hidden_cost_policy / loss_allowed / unit_price_resolution
```

缺失成本不允许默认填 0，可选策略只有：补充成本后求解、
标记为非竞争项排除、用成本区间做情景分析输出利润上下界。

## 5. 系统架构

计算内核（`src/bidpricing/`）+ 网页报价平台（FastAPI 8000 + 原生 JS 8080）
+ 个人工作台（3456）+ Agent 边车（8010），详见仓库地图与数据流（原 HANDOFF §3–§4，
已并入 `README.md` 目录结构，不再重复）。

界面不直接操作求解器内部对象；`api/app.py` 是薄入口，业务逻辑在纯 Python 模块（可单测）。

## 6. 产品架构原则（ROADMAP §2，原样保留）

界面不直接操作 `Phase1Instance`，所有计算经过应用服务层；
所有用户输入先形成版本化 `QuotePolicy`，再传给求解器。

```text
用户界面（上传/参数/方案/异常/导出）
  → 项目会话层（ProjectSession / QuoteScenario：版本、快照、审计、状态）
  → Excel 导入层 + 口径与参数层
  → 统一报价数据模型（QuoteItem / Cost / QuotePolicy）
  → Phase 1 + Phase 2（求解、复核、对拍）
  → 结果、对比、Excel、风险提示、审计快照
```

## 7. 已知缺口（现状，非计划）

1. **固定/隐形成本模型**（P1）：直接归属、分摊、项目固定费用分列可追溯。
2. **模板适配层**（P1）：模板版本、列位置映射、友好错误。
3. **无最高限价项**：识别与提示存在；不能自动优化、无完整录入分摊服务。
4. **多方案对比**：支持同项目方案变体对比；跨项目对比被 400 阻断（产品决策，非缺口）。
5. 若各清单成本构成差异较大，建议把成本构成从项目级扩展为逐项可抵扣占比（ADR-0035 遗留 1）。

细化的路线任务以 [`tasks.json`](tasks.json)（机器可读）为准；
变更历史以 [`../CHANGELOG.md`](../CHANGELOG.md)（里程碑级）为准。

## 8. 设计纪律（13 条，原 HANDOFF §10 原样保留）

1. 状态快照会过期：生成物不是事实源；事实源是代码、配置和现场复算。
2. 成本含税/报价不含税不可直接相减，必须声明税率与抵扣方式。
3. 空限价不是零限价：空值 = 无最高限价，零值 = 明确零价。
4. 低价确认 ≠ 废标判定；留痕字段一旦生成即冻结。
5. `p_by_id` 假设 item_id 唯一；重复键必须显式阻断，不能静默覆盖。
6. MILP 目标值不是最终可信利润，必须独立复算结算收入并核对总价。
7. 方案 JSON 命名 `<报价金额>_<id>.json`、Excel 命名 `<项目名称>-<报价金额>.xlsx`；文件名即契约。
8. `project_id` 是唯一凭证，只存真实 UUID；展示/目录用 `project_name`。
9. 默认目录调用时解析，不得在模块定义时绑定，否则用户隔离失效。
10. 新增阈值必须加配置—实现—测试三方一致性检查。
11. 用户输入必须转义：进 `innerHTML` 前过 `esc()`。
12. 改前端后递增版本查询串（如 `?v=`），否则浏览器缓存加载旧脚本。
13. 方案持久化以库为唯一真相，且按用户一库一文件；种子迁移只在库文件不存在时执行（ADR-0037）。

## 9. 接手者起手式

1. 读 `../README.md` → `STATE.md`（自动生成）→ 本文件 → `adr/` 中与报价规则、C13、结算、低价确认相关的 ADR。
2. `git status --short` 了解工作区；`outputs/` 等为本地数据，不清理他人改动。
3. 运行全量测试 + `contract-check` + `status --write`。
4. `.\run.ps1` 启动，做一次默认 50% 计算和一次「低于 50% 未确认」测试。
5. 修改模型代码后：先补最小单元测试再改主流程；求解器结果必须独立复算；
   条款解释写入配置/ADR，不留在聊天记录。

## 10. 启动与运行（Windows 一键）

`.\run.ps1`：先对解释器做**能力探测**（真跑 `import ssl,venv`，逐个候选试，
跳过 `WindowsApps` 下的 0 字节应用执行别名占位符与 `_ssl` 加载失败的残缺安装），
首次运行在仓库内 `.venv` 建隔离环境并从 `requirements-web.txt` 装依赖（不污染系统 Python）；
探到 `/api/health` 与首页均 200 才报成功。解释器钉死：仓库根 `.python-path`
（单行绝对路径，已 gitignore）或环境变量 `BIDPRICING_PYTHON`。详见 `README.md`
「网页应用：安装与启动」与 `tests/test_run_script.py` 守住的启动器判据。
