# ADR-0002：判定时点必须与消耗时点对齐（机制层 / 数据层分离）

- **状态**：已采纳（accepted）
- **对应任务**：T00-01（`adjustment_scope`）、T00-06（可竞争性分类）
- **证据**：commit `315f53d`（tag `options-phase-split-v1`）、commit `a17e07c`（tag `classification-split-v1`）
- **来源**：用户在评审中两次提出质疑（"为何一定要现在确定"、"为什么需要真实清单"）

## 背景

本项目在两天内犯了**两次同型错误**，两次都由用户发现，且都不是编码错误而是**判据归属错误**：

| # | 被误置的判据 | 错误后果 |
|---|---|---|
| 1 | `adjustment_scope` 的**取值**被挂到 Gate 0a | 未选它 → Gate 0a BLOCKED → 连带阻塞 WP1/WP2/WP3（解析器、配置层、判定层）。**用一个求解期才需要的选择，卡住了早期开发。** |
| 2 | 逐项可竞争性分类表（某项目的清单数据）被放进 Gate 0a 受控制品 | 「提供真实招标清单」被写成 WP1 的开工前置条件。**用一个项目的数据，卡住了跨项目复用的机制开发。** |

两次的形态完全一致：**把「某一次运行才需要的东西」提前到「开工时需要的东西」**。

## 决策

### 一、判定时点由消耗时点决定

一个条件该挂在哪个闸门，不取决于它"重不重要"，而取决于**谁在什么时候真正需要它**：

| 问题 | 归属 |
|---|---|
| 不满足它，**代码就写不出来**（接口未定、规则未定） | **Gate 0a**（开工前） |
| 不满足它，**代码能写但跑不了**（取值未选、项目数据未填） | **Phase 0 输入门**（求解前） |
| 不满足它，**求解能跑但结论不可信**（口径未冻结、成本未定） | **Gate 0b**（WP4 前） |

判据口诀：**「机制就绪」与「取值已定」是两个不同的时点，不得合并判定。**

### 二、机制层与数据层物理分离

凡是同时具备「跨项目复用的规则」与「随项目而异的取值」两面的对象，**拆成两份制品**：

| 层 | 内容 | 归属 | 变更频率 |
|---|---|---|---|
| **机制层** | 有哪些角色 / 规则集如何选 / 字段字典 / 解析协议 | Gate 0a 受控制品（hash 绑定） | 极少，进版本 |
| **数据层** | 本项目选了哪个值 / 本项目每条清单归哪类 | Phase 0 输入制品 | 每项目一份 |

落地的三对拆分：

```
adjustment_scope       →  选项定义（selection_options.py，机制）
                           取值落值（config/project_selection.json，数据）

可竞争性分类            →  config/competitiveness_classification.json（规则书，机制）
                           config/project_classification_table.json（逐项落值，数据）

规则集选择              →  rule_sets/*.py（两版实现的机制，必须同时存在）
                           本次选中哪一个（selector 的输出，数据）
```

### 三、配置冲突在两个时点下都必须 BLOCKED

拆分不等于「放宽」。
若某取值在**当前规则集下根本不合法**（例如 2013 项目落 `FULL`，而 §9.6.2 明文分段），
这在 Gate 0a 与 Phase 0 输入门下**都判 BLOCKED**——不因时点靠前而放行，
也不静默改成合法值。静默覆盖会让「人工落了什么」与「系统用了什么」的差异从审计链上消失。

## 理由

1. **契约本身就要求两条分支并存**。WP3/WP4 必须**同时实现** `FULL` 与 `SEGMENT`
   两条代码路径，选择只决定运行时走哪条。既然如此，未选不影响分支能否开工——
   把它当开工前置，等于凭空造出一个依赖。
2. **规则书不会因为没给清单而写不出来**。分类规则书（角色集合、启发式信号、覆盖范围）
   是跨项目复用的知识；逐项落值才是项目数据。把两者放一个制品里，就会用数据阻塞机制。
3. **错误归因需要时点区分**。「机制没写好」与「项目数据没填」是两类完全不同的失败，
   混在同一闸门里，报告只会给出一个 `BLOCKED`，无法指出该找开发还是该找业务。

## 后果

- **正面**：Gate 0a 从 `BLOCKED 6/8` 变为 `PASS 8/8`，WP1/WP2/WP3 立即放行，
  技术侧零剩余阻塞——不再需要用户先给任何项目数据才能开工。
- **正面**：失败报告可归因。现在能明确说出「Phase 0 输入门 BLOCKED：缺项目分类表」，
  而不是笼统的「闸门没过」。
- **负面**：闸门从一个变成三个（Gate 0a / Phase 0 输入门 / Gate 0b），
  `evaluate_gate_0` 的返回结构变复杂；`summary.phase_0` 需由两个条件共同决定。
- **约束**：新增的 `check_project_input_artifacts` 在**注册表未声明制品时判 BLOCKED**，
  不允许"空真通过"（vacuous pass）——否则误删声明会让闸门悄悄放行。

## 相关判据

- `gate0.check_selectable_option(..., phase="gate_0a")` — 只判机制就绪，未定 PASS；
- `gate0.check_selectable_option(..., phase="phase_0")` — 判取值，未定 BLOCKED；
- `gate0.check_project_input_artifacts` — 项目级输入制品（文件存在 → 行非空 → 逐行字段与角色合法）；
- `status.effective_status` — 人工状态为 `partial` 时**不被制品冻结覆盖**
  （冻结只证明机制就绪，不代表项目数据已填，T00-06 即此情形）。

## 反面清单（今后不得再犯）

- ❌ 把「本项目选了哪个值」写进注册表当受控制品；
- ❌ 把「某项目的清单数据」当作跨项目机制的前置；
- ❌ 用 `default` 值兜住未选择状态（断言 6① 静态扫描已拒绝）；
- ❌ 在某个时点放行、在另一个时点也放行（配置冲突必须两处都拦）。
