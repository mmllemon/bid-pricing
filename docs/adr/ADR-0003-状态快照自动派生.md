# ADR-0003：状态快照必须自动派生，禁止手工誊抄

- **状态**：已采纳（accepted）
- **对应任务**：工程基础设施（非路线原始任务）
- **实现**：`src/bidpricing/status.py`、`tools/extract_tasks.py`、`cli status`
- **产物**：`docs/STATE.md`（生成物）、`docs/tasks.json`（结构派生 + 状态人工）

## 背景

本项目在两天内出现**三次同型事故**：文档里写的数字与代码实际不符。

| # | 文档写的 | 实际 | 发现方式 |
|---|---|---|---|
| 1 | `README.md`：「Gate 0a 6/8 判据通过」 | 此时已是 8/8 | 用户追问时现场复跑 `gate-check` 才发现 |
| 2 | `DEVELOPMENT.md`：「89 项单元测试」 | 已增长到 98 项 | 现场跑测试才发现 |
| 3 | `DEVELOPMENT.md`：「提供真实招标清单」列为 WP1 开工前置 | 已被 ADR-0002 推翻 | 用户质疑"为什么需要真实清单" |

三次的**根因完全相同**：**数字是手工抄进文档的，而数字的来源在变。**

这个失效模式有三个特征，决定了它不能靠"下次注意"解决：

1. **必然性**——只要来源会变而抄本不动，失配只是时间问题；
2. **隐蔽性**——文档本身不会报错，错误在"有人刚好读到那一行"之前一直存在；
3. **传染性**——下游决策（如"要不要现在给清单"）会建立在过期数字之上。

而项目本身还有一个放大因素：**任务数是 68**。任何要求"每次改动后同步更新 68 行状态"的约定，
在实践中都不成立。

## 决策

### 一、状态快照是生成物，不是著作物

```
bidpricing status --write  →  docs/STATE.md
```

该文件头部写死一条声明，任何打开它的人第一眼就会看到：

```html
<!-- ⚠ 本文件由 `python -m bidpricing.cli status --write` 自动生成。
     请勿手工编辑——手写的状态一定会在某次改动后过期。
     要改内容，请改来源：git 提交 / config 注册表 / docs/tasks.json。 -->
```

**改内容只能改来源。** 这条规则把"记得更新文档"从人的义务变成了工具的义务。

### 二、每一段状态都必须现场取自权威源

`status.py` 不做任何"读一份写好的进度文档"的动作。每一段的来源如下：

| 段落 | 来源 | 为什么可信 |
|---|---|---|
| 版本锚点 | `git rev-parse` / `describe` / `status --porcelain` | 提交历史不可篡改 |
| 闸门状态 | `gates.gate0.evaluate_gate_0()` | 与本地/CI 判据**同源同值** |
| 制品冻结 | `config/gate0_registry.json` 的 hash 字段 | hash 由制品内容算出，改则失配 |
| 测试结果 | **现场运行** `unittest` | 不接受"上次跑过"——缓存会撒谎 |
| 任务进度 | `docs/tasks.json` + 证据核对 | 见下条 |
| 遗留项 | 各配置的 `known_limits` / `freeze_blocker` | 自声明，不被汇总掩盖 |

### 三、任务结构派生、状态双轨（人工声明 + 证据核对）

任务板拆成两类字段，**互不污染**：

```
结构字段（id/wp/title/deliverable/deps）  ← 单向派生自路线文档，脚本重跑即更新
状态字段（status/note/evidence）          ← 人工维护，脚本永不覆盖
```

派生方向是**单向**的：`impl_plan_v321.md → docs/tasks.json`。
路线升版（v3.3 已在文档中登记待办）时，只需重跑：

```bash
python tools/extract_tasks.py            # 重新提取结构，保留全部人工状态
python tools/extract_tasks.py --check    # CI 用：结构漂移则退出码 1
```

`--check` 是这套机制的关键闭环：**路线文档改了而任务板未重新提取时，构建应当失败**，
而不是让任务板悄悄过期。

### 四、状态须有代码证据支撑

`tasks.json` 中每条任务可声明 `evidence`：

```json
{"kind": "artifact", "key": "field_schema_version"}   // 制品已冻结（hash 非空）即成立
{"kind": "module",   "path": "src/bidpricing/..."}    // 文件存在即成立
```

派生规则（`status.effective_status`）：

```
人工声明优先；人工未声明（not_started）而证据成立 → 判为 done。
人工声明为 partial 时不被证据覆盖。
```

两条分支各有理由：

- 第一条消除**"证据能证明的事还要人再写一遍"**。T00-02（字段字典冻结）的证据就是
  「`field_schema_version` 有 hash」——制品一旦冻结，任务事实上就完成了。
  若因"没人去改状态"而把它列为待办，手工誊抄就又成了必要环节，漂移随之回来。
- 第二条防止**用证据掩盖未完成的另一半**。T00-06 的规则书已冻结（证据成立），
  但项目级落值表仍为空——此时若把 `partial` 覆盖成 `done`，就等于宣布一个
  尚未完成的任务已完成。**制品冻结只证明机制就绪，不证明项目数据已填。**

## 理由

1. **工具的义务比人的义务可靠**。要求人"记得同步"，在一个 68 任务的长期项目上
   必然失败；要求脚本"每次重新采集"，则不需要任何人记得任何事。
2. **证据核对把"已完成"从声明变成断言**。「已完成」不再是某人在文档里写的一句话，
   而是可由代码复核的命题——这直接决定了跨会话交接时，下一个人能否信任前一个人的结论。
3. **`--check` 让过期可被检测**。没有校验的派生只是"更省事的誊抄"，
   失配后依然无人知晓；有了校验，失配会在构建阶段被机械拦下。

## 后果

- **正面**：`STATE.md` 的每一个数字都可复算。本次生成即验证了此前三处漂移已消除
  （闸门 8/8、测试 98 项、Gate 0a 无阻塞项）。
- **正面**：新会话接手只需读两个文件——`docs/STATE.md`（现在在哪）
  与 `docs/adr/`（为什么这样做）。
- **负面**：`status` 命令需现场跑测试（约 0.1 秒，可接受），
  且依赖 `git` 可用（不可用时降级为 `unknown`，不让整个快照失败）。
- **约束**：`docs/STATE.md` 必须纳入版本控制——否则"上次交接时状态如何"无从追溯；
  但它同时是生成物，故**冲突时以重跑为准，不做手工合并**。
- **约束**：`tasks.json` 的结构字段严禁手改。手改会在下次 `--check` 时报错。
