# ADR-0005 恒等式闭合不得用作数据完整性判据

- 状态：已采纳
- 日期：2026-09-16
- 关联：ADR-0002（判定时点与机制数据分层）、T00-06B、T01-02C、T06-06
- 证据：`tests/data/xiyong_l_district/pair.json`、`tests/test_identity.py::ClosureIsNotCompletenessTest`、commit（本 ADR 同批）

## 背景

总价恒等式是本模型的中心不变量：

```
计税基数 = 分部分项 + 措施 + 其他 + 规费 − 甲供材料费
增值税   = 计税基数 × 增值税率
附加税   = 增值税 × 附加税率
税金     = 增值税 + 附加税
总价     = 分部分项 + 措施 + 其他 + 规费 + 税金
```

2026-09-16 拿到第一份**真实**的同项目「限价 / 报价」配对
（西永L分区公立学校一期工程等项目配电工程）后，对该不变量做了两侧核验：

| 侧 | 结果 |
|---|---|
| 报价 | 全部判据 PASS，残差 **0.0000**，总价 1,416,251.85 |
| 限价 | 全部判据 PASS，残差 **0.0000**，总价 8,623.74 |

问题出在限价侧：它的表-04「分部分项工程费」是**空的**，表-12 的增值税只按
措施项目费计得，所以整条链条**自洽**——可是它逐项单价合计其实是 **1,374,238.77 元**。

**一个漏掉了 99.4% 金额的汇总表，通过了恒等式的全部检查。**

## 决策

**恒等式判据只回答「已声明的分项彼此是否自洽」，不回答「分项是否齐备」。
任何把闭合当作完整性证据的用法一律禁止。**

数据完整性必须由**独立判据**承担：

1. **输入保真判据**：`Σ(逐项明细) == 表列小计`——本模块的
   :func:`bidpricing.identity.check_component_sum`。它比对的是**明细与汇总**，
   而恒等式比对的是**分项与总价**，两者覆盖的失效模式不同：
   - 明细漏行 / 把分部标题行当明细 / 合计行重复计入 → 只有输入保真能发现；
   - 税率用错 / 基数含错减项 / 汇总漏计某项 → 只有恒等式能发现。
2. **覆盖度判据**：清单覆盖面检查（T00-06 的 `assignment_scope`）——
   分部分项、表-09、表-10、表-11 四类清单必须齐全，缺任一类即为此类缺陷。
3. **两侧闭环**：有配对数据时（限价 + 报价），同时核验两侧并**比对差异**；
   仅一侧通过不构成证据。

## 后果

- `identity-check` 输出的「结论：恒等式闭合」**不得**被读作「该项目数据完整」。
  报告用语已相应收窄。
- 恒等式因此**不得**作为 Gate 放行的唯一判据；Phase 0 输入门另有覆盖度判据。
- 代价是必须维护两类判据而非一类，且两类都要有真实样本背书。
  这个代价是必要的——把两类判据合并，等于让一个漏洞同时躲过两个检查。

## 替代方案与为何不采

| 方案 | 否决理由 |
|---|---|
| 收紧容差（如要求残差恰为 0） | 无效。限价侧残差本来就是 0，问题不在精度。 |
| 要求「分部分项工程费 > 0」 | 只能挡住本样本这一种形态（整块缺失）；挡不住「漏 3 行」这类部分缺失。 |
| 用恒等式 + 人工复核 | 违反 ADR-0003（状态必须自动派生）。人工复核不构成机械判据。 |
| 只信配对数据中的报价侧 | 报价侧完整是**本样本的偶然性质**，不是可依赖的规律。 |

## 与 ADR-0002 的同型性

两件事性质不同却容易被塞进一个判据——这是本项目第三次遇到同一模式：

| ADR | 被混为一谈的两件事 | 正确切分 |
|---|---|---|
| 0002 | 机制就绪 / 取值已定 | Gate 0a / Phase 0 输入门 |
| 0002 | 跨项目复用的规则书 / 一项目一份的落值表 | 同上 |
| **0005** | **已声明分项自洽 / 分项齐备** | **恒等式 / 输入保真 + 覆盖度** |

**通用判据（第三次确认）**：一个判据若能同时被两类不同性质的失败通过，
说明它承担了它不该承担的职责，必须拆分而不是收紧。
