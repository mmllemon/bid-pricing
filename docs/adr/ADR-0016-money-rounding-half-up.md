# ADR-0016：金额舍入只有一个入口 —— 四舍五入，不是银行家舍入

- 状态：**已接受**（2026-09-17）
- 关联：`config/precision_profile.json → rounding.rule`、ADR-0014（总价分解）、T06-06

---

## 背景

`precision_profile.json` 的舍入规则逐字写着：

> 「分项**四舍五入**至 0.01 元，汇总后再舍入一次；禁止逐项舍入后累加」

而实现里用的是 Python 内建 `round()`——它做的是**银行家舍入**
（round-half-to-even）：

```python
round(0.125, 2)  →  0.12      # 规范要求 0.13
round(2.675, 2)  →  2.67      # 规范要求 2.68（二进制表示所致）
```

两个差异都不是理论问题：

1. **半厘值的舍入方向相反**。费率相乘极易产出半厘（`x × 9%`），
   1,234,567.89 这类金额上并不罕见；
2. **二进制的方向不可预测**。`2.675` 向下、`0.125` 向上，取决于该小数在
   二进制下的表示——这正是「时好时坏」型缺陷的典型形态。

后果不是「差一分钱」那么轻：它会让同一笔金额在**不同模块**里舍出不同结果，
于是恒等式在汇总处差 0.01 元——**恰好落在 `eps_abs` 容差上**，形成闪烁判据：
同一个项目，今天过、明天不过，而两次运行的数据完全相同。

## 决策

### 1. 全仓唯一入口 `src/bidpricing/money.py`

* `money(x)` —— 四舍五入到 0.01 元（`Decimal` + `ROUND_HALF_UP`）；
* `money_sum(iterable)` —— `Decimal` 精确累加后**整体舍入一次**，
  即「汇总后再舍入一次」，与「逐项舍入后累加」是两件事；
* `is_money_aligned(x)` —— 自检某数是否已是分位精确值。

实现细节：先 `str(x)` 再进 `Decimal`，避免把 float 的二进制尾巴
（`0.1 + 0.2 = 0.30000000000000004`）当成有效数字。

### 2. 只用于**金额**，不用于容差与残差

`precision_profile.eps_*` 里的容差是绝对/相对量，不是金额，
**不得**套 `money()`。判据里报告残差用 `round(x, 4)` 是显示精度，同理不套。

### 3. 同一规则在两处实现，就是口径分叉

`identity.py` 与 `total_price.py` 原本各写一份舍入。已统一到 `money.py`——
理由与 `contract-check` 拦「同一规则在两份制品里说法不同」完全一致。

## 影响

* 新增 `tests/test_money.py`（9 用例），其中
  `test_discriminating_cases` 直接断言 `money(0.125) != round(0.125, 2)`——
  把「用错舍入」变成可失败的断言，而不是等它在某天以 0.01 元偏差现身；
* `identity.py` / `total_price.py` 全部金额运算改走 `money` / `money_sum`；
* **真实样本结论未变**（1,416,251.85 与源工作簿一致）——说明本样本此前没有
  踩到半厘分界，属**潜在**缺陷而非既成错误；

## 槽点记录

`test_exact_decimal_accumulation` 第一版用 `sum([0.1]*10) != 1.00` 断言浮点误差，
在 **Python 3.12+ 上失败**——因为 CPython 3.12 起给内建 `sum()` 加了浮点补偿求和
（Neumaier）。改用显式循环累加才能暴露朴素浮点误差。

**教训**：断言「某个语言特性会有误差」时，该特性本身可能正在被改进；
写此类用例要直接构造误差，而不是依赖某个 API 的实现细节。
