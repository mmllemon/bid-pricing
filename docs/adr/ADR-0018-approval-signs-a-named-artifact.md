# ADR-0018 审批签的是「责任制品」，且必须逐角色分别签

- 日期：2026-09-17
- 状态：已采纳
- 触发：用户提问「approvals —— 合同/造价/法务/项目经理四角色签署，这又是什么啊」

## 这个门禁的来历

路线隐藏依赖 19（v3.2.1 新增，闭合复审 §5.6）原文：

> `all_required_approvals = true` 若未定义审批角色、人数与各自签署的制品 hash，
> Gate 0b 可被**单人勾选**通过，业务口径并未真正冻结——熔断点形同虚设

背景：v3.2 的 Gate 0b 只要求一个布尔位 `all_required_approvals = true`。
任何人都能勾选它，所以它防不住「口径没人真的看过就被当成已冻结」。
v3.2.1 把它改成「四个角色，每人签署一份制品的 hash」——
签名绑定 hash 带来一个真实性质：**制品一改，签名自动作废**，
不可能出现「签完之后内容被换掉」。

## 实现里仍存在的漏洞

v3.2.1 的定义只要求「每角色签署制品 hash **非空**」，**没有规定签哪个制品**。
于是写一个与任何制品都无关的字符串（`sha256:aaaa...`）同样能过关——
这跟打一个勾没有本质区别，只是把勾换成了看着像 hash 的字符串。

## 决策

`_check_approvals` 三档语义，逐角色判定：

| 情形 | 判定 |
|---|---|
| 有条目 + `by` 署名 + 签署了**该角色全部责任制品** + 每条 hash 与制品现值一致 | 计入已签 |
| 显式声明 `NOT_COVERED` + 给出理由 | **WARN**，不阻塞 |
| 缺条目 / 无 `by` / 无制品 / 签了未声明制品 / hash 为空或失配 | **BLOCKED** |

三条关键规则：

1. **签署对象必须指向已声明制品**，且必须覆盖该角色的**责任制品**
   （注册表 `responsibility` 角色→制品映射）。
   签非责任制品与打勾无异，故判 BLOCKED。
2. **签名 hash 必须与制品现值一致**。制品在签署后被改动 → 签名失效 →
   BLOCKED 并提示「须重签」。这是 hash 绑定签名唯一真正的价值所在。
3. **`NOT_COVERED` 是真话，不是假审批**。`signed = {}` 是「没人说过」，
   `NOT_COVERED` 是「说了没人负责」——前者是 BLOCKED，后者是 WARN。
   声明 `NOT_COVERED` 却不给理由，判 BLOCKED：**「本角色无人负责」本身
   是断言，须写明原因**（ADR-0007 同一判据）。

## 为什么允许一人承担多个角色

四角色是**专业视角**的划分，不是**人数**的划分。小团队里同一人兼任是常态，
禁止它只会逼出「随便找个人签」或「伪造四个名字」——比诚实记录更糟。

真正的防线不是人数，而是**逐角色分别签署具体的制品**：
它把「一次模糊确认」变成「多次针对具体文件的确认」，这个改进与人数无关。
一人兼四角色时，他仍须逐个制品看过才能签出四个不同的 hash。

**责任制品映射（`responsibility`）是模型建议的职责划分，可调整**——
它记录的是「这份制品的内容属于哪个专业的判断范围」，不是人事安排。

## 为什么 NOT_COVERED 不阻塞测算

判据：**缺失让算式算不出/算错 → BLOCKED；只让结论说不清出处 → INFO/WARN**
（ADR-0013 台账不是关卡）。

四角色中法务视角缺失，不改变任何算式——它改变的是**风险认知**
（例如不平衡报价是否可能被认定为异常低价）。因此：
不阻塞 WP4，但必须在报告中作为风险敞口显式暴露，而不是静默通过。

## 后果

- Gate 0b 的审批项从「签个 hash 就行」变成「签对文件、签对角色、签后不许改文件」。
- 本项目（一人）的落地方式：逐角色签各自责任制品；
  确无对应专业承担的角色写 `NOT_COVERED` + 理由。
  **签署是责任归属声明，Agent 不得代为填写**（ADR-0007）。
