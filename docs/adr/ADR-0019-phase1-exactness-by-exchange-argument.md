# ADR-0019：Phase 1 精确性用交换论证证明，条件分两组、verdict 只看 A 组

- 状态：已采纳（2026-09-17）
- 任务：T04-00
- 制品：`config/phase1_exactness_spec.json`（sha 由 `freeze` 写入）
- 实现：`src/bidpricing/solver/{instance,exactness,cases}.py`、`cli phase1-check`
- 相关：模型设计 v0.3-R2 §7.2.1/§7.3；实施路线 v3.2.1 §4.1、§5.3 S4

## 背景

Phase 1 的「按 `r_eff` 降序排序 + 二分求 λ + 贪心定容」解析算法，其存在理由是
「绝大多数项目实例有闭式解，复杂度 O(n log n)」。但这条理由只有在**算法与 LP
解同一问题时**才成立。

实施路线 v3 的独立互审指出（U5）：**等价性在 T04-00 完成前尚未证明**，因此原
§4.1 实验名「数学等价性实验」是**结论前置**——名字里已经写好了尚未证明的结论。
v3 把它更名为「Phase 1 解析候选解一致性实验」，并把 T04-00 定为 P0 前置：
未完成前，两条路径不一致**不能**判为「模型有 bug」。

同时 v3.2.1（P2-⑩）要求对拍结论必须依附 T04-08 的独立性验收。这两条约束合在
一起，给 T04-00 提出一个不小的要求：它给出的证明路径**必须与 T04-01 的实现独立**，
否则「证明」与「实现」共享同一个误解，独立性验收就没有对象。

## 决策

### 一、用交换论证（exchange argument）证明，不用 KKT

定理 T1 的证明只使用一个操作：对两个都处于内点的项 i、j，作交换
`p_i += δ/q0_i`、`p_j -= δ/q0_j`（保持 C1 与箱型），目标变化
`ΔZ = δ·(r_eff_i − r_eff_j)`。最优性要求该值在两个方向上都 ≤ 0，故
`r_eff_i = r_eff_j`。同理可推「内点项的对偶门槛夹在顶格项与触底项之间」。

**为什么不走 KKT**：KKT 是 T04-02A/04-02D 的实现路线（对偶变量、互补松弛、
平稳性残差都要在 Phase 3 复核里算）。若 T04-00 也用 KKT 证明，那么当 KKT 的
**公式本身写错**（例如把 C1 的系数写成 `q1` 而不是 `q0`）时，证明与实现会同时
按同一个错误成立——这正是 T04-08 要消除的共因错误。交换论证不引用任何对偶量，
是一条真正独立的路径。

### 二、条件分 A / B 两组，verdict 只看 A 组

| 组 | 条件 | 违反后果 |
|---|---|---|
| A（EXACTNESS） | EC-1 作用域完备 · EC-2 排序键正确 · EC-3 权重正 · EC-4 系数非负 · EC-5 非退化 · EC-6 软约束不激活 · EC-7 可行域非空 | 阈值分割解**不是**最优解 ⇒ `INAPPLICABLE`，交 Phase 2 |
| B（IMPLEMENTABILITY） | EC-8 舍入可调和 · EC-9 上界有限 | 数学结论仍成立，但算法/输出环节须走分支 ⇒ 记入 `implementation_notes` |

**理由（这一条是被实证逼出来的）**：最初把 EC-8 放在 A 组，结果是**任何一个
实例都判不出 `EXACT`**——因为舍入残差上界 `0.005·Σq0` 几乎总大于
`eps_total = max(0.01, 1e-9·B)`（附录 B 例 2R 这种 n=2、Σq0=200 的微型实例，
上界 1 元也超过 0.01 元）。一个永远为 `INAPPLICABLE` 或永远需要附注的 verdict
等于没有 verdict。

把「数学上是否精确」与「输出环节是否需要额外义务」拆开之后，两者各自有了
区分力：本项目的真实结论是**「Phase 1 数学上精确，但舍入调和环节不可省、
且必须内建空 cap 分支」**——这句话比「不适用」或「适用于大多数情况」都更有用。

### 三、EC-2 只比较**严格偏序**，「平」不算「排序不同」

EC-2 的判据形态是「两个候选排序键会不会给出不同的降序排列」。第一版实现把
`1 + alpha_i` 也当作候选键——但 `alpha` 全为 0 时它对**全部项**取同一值，
即「平序」。把平序算作「不同排序」的结果是几乎每个实例都 WARN，判据随即
失去区分力。

现判据：存在 `(i,j)` 使 `(r_i − r_j)·(r_eff_i − r_eff_j) < 0` 才判 WARN。
这正是 §7.2.1 反例集列出的两条真实情形（「跨越阈值造成排序倒挂」与
「`alpha_i` 逐项不同导致排序与 `r_i` 不一致」）。退化（平）由 EC-5 单独管。

### 四、反例的 `expected` 做**双向**比对

单向比对（制品说了什么就查什么）留了一个真实漏洞：制品漏写一条 FAIL 时，
实现多判一条 FAIL 反而**不报错**——判据整体变严却没有信号。CE-07 首次运行时
就踩到（EC-5 的平台判定被漏写，实现判了两条 FAIL、制品只声明一条，单向比对
通过）。现实现额外要求：**实现判 FAIL/BLOCKED 的 A 组条件必须在 `expected`
中出现**，不论取值。

### 五、见证层用「误用解 vs 正确解」的数值对照

每个反例给两个解（各自满足/不满足 C1+箱型+C5），断言写成结构化布尔键
（`wrong_solution_feasible`、`wrong_Z_gt_right_Z`、`wrong_competitive_total_gt_B`），
由 `check_solution` 代回原式复算。**不用可执行表达式**：那是一个不受控的求值口，
且失败时无法定位是哪一项不成立。断言值记成三元组 `(键, 制品声明, 实现复算)`——
只报通过/不通过的话，制品与实现同时改错（同一个误解写进两边）时无从发现。

## 影响

- **§4.1 实验的适用范围被限定**：一致性只在 `check_exactness` 判 `EXACT` 的
  实例子集上要求；判 `INAPPLICABLE` 的实例上两条路径不一致是正确行为。
- **T04-01 的定位被收紧**：解析解是 candidate / 上界，不承担最终解职责；
  且只在 T04-00 已证明的适用子集上可用。
- **`compute_r_eff` 与 `settlement_revenue` 成为唯一实现**，放在
  `contracts/pricing_card.py`（它们属规则集机制，不属求解层）。测试用
  `compute_p1` 逐值交叉锁定 `settlement_revenue`，防止出现第二事实源。
- **本项目真实结论**：EC-9 对西永L样本判 WARN（存在不限价项 031301017001），
  故 Phase 1 算法**必须内建「空 cap 项固定为临界项」的分支**，不得依赖
  「所有项都有 cap」这一假前提。
- **顺带修掉一个实现 bug**：SEGMENT 分支的 `r_eff` 原写作
  `(1.0 + increase_threshold) + …`，而 `increase_threshold` 本身已是
  `(1 + θ_dev)`，导致越界段 `r_eff` 被系统性高估（1.6 处算成 2.04 而非 1.24）。
  附录 B 例 2R 的期望值用例抓到它。

## 遗留

1. `§7.1.1-5 时序断言` 目前**空真通过**（尚未有 WP4 Phase 1 构建记录）。
   T04-01 落地后须填入；否则「时序未违反」是因为没有对象可违反。
2. `phase1_exactness_spec` **未登记进任何闸门注册表**——Gate 3 的注册表尚未
   建立，当前 Gate 0a/0b 注册表只覆盖 WP0 制品。是否为其新建 Gate 3 注册表
   属**改动闸门判据集**，须先与用户确认，故本轮未做。
3. EC-5 只给出「存在可容纳总价分配的 `r_eff` 平台」这一**必要**信号，
   不枚举全部多最优解；完整处理留 T04-06B。
4. 真实项目实例入口（从 master 表直接构造 `Phase1Instance`）未开：
   跑 EC 需要 `c_i`，而当前 master 表两侧只有 `cap` 与成本单价，
   `attribution`/`q1_point` 尚未落值。`--instance` 已可用于手工构造。
5. 反例集不覆盖 MILP 模式（C7 升 MILP 后 KKT 不适用，走 T04-07 协议）。
