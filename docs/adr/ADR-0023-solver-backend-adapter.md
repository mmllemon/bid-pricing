# ADR-0023 求解后端适配层的位置：业务不写死求解器、状态分域、导出层自持符号编码

- 状态：已采纳
- 日期：2026-09-17
- 任务：T04-02C（HiGHS backend adapter）
- 相关：ADR-0013（治理三档）、ADR-0015（判据不得自证）、ADR-0019（Phase 1 精确性）、
  ADR-0020（等式容差模式 A）、ADR-0021（LP 形式化，决策三已被 ADR-0022 推翻）、
  ADR-0022（约束编译器）
- 制品：`config/solver_backend_spec.json`（新）、`config/lp_compiler_spec.json`（改）
- 判据：`backend-check`（BB-01..BB-09）

---

## 背景

实施路线给 T04-02C 的一句话是「**业务逻辑不写死求解器；换后端只改配置**」。
这句话是可证伪的，但它的三种常见「假成立」都很容易蒙过人工复查：

1. **靠回退链蒙对**——配置指向的后端其实没被用上，实际跑的是另一个；
2. **名字在分支里写死**——配置只是个摆设，`if backend == "pulp"` 才是真相；
3. **替身后端跑不通**——所谓「可替换」从未被真的替换过一次。

同时 T04-02B 留下一条明确的挂账：CC-09（PuLP 结构等价）在本机恒为 SKIP，
「导出层没走样」**尚未被验证过**。这一条必须在 T04-02C 里闭合。

## 决策一：适配层是一个模块，不是一层标签

**决定**：全仓只有 `src/bidpricing/solver/backend.py` 可以 import 求解器包、可以调用
`solve()`。业务层（formulation / compiler / contracts / io / cli）只认识
`solve_compiled(CompiledModel) -> SolveResult` 这一个入口与 `SolveResult` 这一个数据类。

**理由**：这是「换后端只改配置」的**可判定形式**。若允许第二个模块 import pulp，
那么「换后端」就必须改两个地方，判据也就无从机械表达。纪律只有落成可静态检查的
性质才有意义，故配 BB-03：AST 扫全仓，求解器包的 import 只许出现在制品声明的模块内
且必须是**函数体内的惰性导入**；`solve()` 调用只许出现在适配层。

**为什么连 `to_pulp` 也豁免**：T04-02B 的 `compiler.to_pulp` / `extract_pulp_structure`
是**导出层**（模型 → 后端对象），属「模型长什么样」的延伸，其 import 已在函数体内。
它豁免的只是 import 白名单，**不豁免** solve 调用白名单——编译器调用 `solve()` 会让
CC-07 的独立性丧失（同一路径既造模型又出解），这与 T04-02B 制品的 `forbidden` 段一致。

**为什么必须惰性**：模块级 import 会让「换后端只改配置」在 import 期就断掉——没装 pulp
的机器连业务模块都 import 不进来，于是判据全部退化为 ImportError，而不是干净的 SKIP。

## 决策二：求解状态与判据状态分属两个域

**决定**：定义九值**归一状态域**，`native → normalized → judge` 两条映射分开：

| normalized | class | judge | 含义 |
|---|---|---|---|
| OPTIMAL | CONCLUSION | PASS | 已证最优 |
| FEASIBLE | CONCLUSION | WARN | 找到可行解，最优性未证 |
| INFEASIBLE | CONCLUSION | FAIL | 已证无可行解 |
| UNBOUNDED | CONCLUSION | FAIL | 已证无界 |
| AMBIGUOUS | CONCLUSION | WARN | 后端自己分不清无解/无界 |
| UNSOLVED | NO_CONCLUSION | BLOCKED | 正常退出但既无解也无证明 |
| ERROR | NO_CONCLUSION | BLOCKED | 模型非法 / 求解器内部错 |
| UNAVAILABLE | NOT_RUN | SKIP | 后端包未安装（探针产出） |
| UNSUPPORTED | NOT_RUN | BLOCKED | 能力不足或条目未实现（选择层产出） |

**理由**：求解器的答案是**业务结论**（这个模型有没有解、最优值多少），判据的答案是
「这一环有没有走样」。把两者塞进同一个枚举，正是本仓反复出现的根因——把两种机器上
应可区分的状态混成一种。

**四条关键裁定**：

1. **AMBIGUOUS 独立存在。** HiGHS 有 `kUnboundedOrInfeasible`（它自己说分不清），
   PuLP 有 `Undefined`（把「没返回解」与「无界/不可行未定」塞在同一格）。折进
   INFEASIBLE 是**无据断言**；折进 ERROR 是**无据归因**。两者都不行，故保留歧义态，
   并给它一个消歧义务。
2. **「超时」不含结论。** `kTimeLimit` / `kIterationLimit` / `kSolutionLimit` /
   `kInterrupt` 只说求解器**为什么停**。有 incumbent ⇒ 至少兑现了一个可行解（FEASIBLE，
   最优性未证）；没有 ⇒ 什么都没拿到（UNSOLVED）。合并两者，会把「有解但未证最优」
   报成「没算出来」，或反向把「没算出」报成「有解」。
3. **UNAVAILABLE 与 UNSUPPORTED 分属不同档。** 前者是环境缺失（包没装——换台机器就好）
   ⇒ SKIP + 复跑条件；后者是机制缺失（配置指了一个做不到的组合——换机器也一样）
   ⇒ BLOCKED。若把两者都判 SKIP，一个把 MILP 交给 LP-only 后端的配置会以「没跑」的
   样子长期留在台账里，永远等不到复跑条件被满足。
4. **原生别名表整张住制品。** 适配层源码里不得出现任何一个别名串（BB-05 的静态子判据）。
   别名只在运行时从后端对象读回。

**这条判据的自家教训**：BB-05 首版按纯文本 grep 源码，把模块自己 docstring 里
「为什么 `kUnboundedOrInfeasible` 不能折进 INFEASIBLE」的说明文字报成违规 ——
判据把正常实现报成违规。改为 AST 取字符串字面量**且排除 docstring**：要拦的是
「代码路径上有一份硬拷贝」，不是「文档里提到了这个词」。这与 CC-12 是同一条教训。

## 决策三：能力不足即 BLOCKED，绝不降级

**决定**：模型形态（LP/MILP）决定所需能力；所需能力必须是所选后端能力集的子集，
不足则 UNSUPPORTED ⇒ BLOCKED。`never_downgrade_capability = true`；
声明为**未实现**的条目同样判 UNSUPPORTED 且**不回退**。

**理由**：把含二元变量的模型交给只支持 LP 的后端，后者会**静默放松整数性**并返回一个
看起来合理的错解。这与 T04-02B 里 C7 共用 M 是同族失效——不报错、结果看着合理、
结论是错的。同理，若「声明为未实现」也能靠回退拿到解，那么「能力矩阵声明了什么」就与
「实际算了什么」脱钩；制品是真相来源的前提是它的取值有后果。

**未识别形态取并集**（LP ∪ MILP）：宁可 BLOCKED，也不得按低要求放行。

**BB-02 用「忽略可用性的规划解」判定**：这条判据问的是「模型 → 所需能力 → 制品选的
条目能不能覆盖」这条**配置链**，与那台机器装没装包无关。若把可用性算进来，在零依赖
环境里这条判据会退化成环境探测。同理 BB-06 也忽略可用性——它问的是「配置 → 选谁」的
映射是否单射。

## 决策四：CC-09 复跑，且先把覆盖面补上

**决定**：在 CC-09 的比对项中补上**逐行系数多重集**、**目标方向**、**目标常量**，
并把行比对从「按下标」改为「按指纹多重集配对」（与 CC-02 同构），然后复跑。

**理由**：首版只比变量集、行数、逐行 sense、逐行 rhs 与目标系数。而导出层最常见的
三种走样恰好落在未被覆盖的区间里：

1. 系数漏乘/错位；
2. 目标常量丢符号；
3. 最大化 ↔ 最小化反向。

三者都满足「变量集相同、行数相同、sense 相同、rhs 相同、目标系数相同」。按本仓既有
原则，这属**覆盖面不足**而非容差不对 ⇒ 补全覆盖面，而不是收紧容差。

按 index 逐行比对本就该改：它隐含假设了「`CompiledModel.rows` 的顺序 == PuLP 约束的
插入顺序」。该假设从未被声明，一旦建模器改字典行为，判据会以「rhs 不同」的名义报出
一堆假 FAIL，把真问题（某行的系数错了）淹没。

**复跑结果：首跑即 FAIL 两处，都是本机从未跑过这条判据所掩盖的真问题。**

### 决策四之①：导出层把变量名交给建模器净化（真 bug，静默）

**现象**：PuLP 的 `LpVariable` 在**构造时**把 `+ - / > [ ]` 与空格一律替换成 `_`。
于是：

- 模型符号 `p_P-DEC` 在导出后变成 `p_P_DEC`，适配层按符号回读取值**一个也取不到**，
  解被判「全部变量缺失」；
- 更糟：两个不同符号净化后同名 ⇒ **两个决策变量合并成一个**。实测
  `LpVariable("a-b")` 与 `LpVariable("a_b")` 的 `.name` 都是 `a_b`。

**为什么不报错**：净化发生在建对象时，不产生异常、不产生告警。合并后的模型仍然可解，
只是解的语义已经不是原来那个问题了。

**修法（决策）：导出层自己拥有一套可逆编码**，把符号映到建模器一定不会改动的字符集，
而**不是**在适配层做字符串修补（那是把建模器的规矩抄进业务侧）。

- 白名单 `[A-Za-z0-9_]` 原样保留，其余字符编码为 `~` + 四位十六进制码（`~%04x`）；
- 转义引导符 `~` 也在白名单里，但它**已实测被建模器放行**（见下），故解码无歧义；
- 编码/解码只有一份实现（`compiler.encode_symbol` / `decode_symbol`）；
  适配层通过 `compiler.pulp_name_map` 取映射，不自行拼名字。

**实测清单**：2026-09-17 穷举全部可打印字符（PuLP 3.3.2），建模器**只**改动七个字符
——`+ - / > [ ]` 与空格。该清单记在 `compiler.MODELER_MANGLED_CHARS`，并有单测断言
编码结果与之不相交。白名单比黑名单稳，故判定用白名单，黑名单只用于断言。

**为什么这条要单列一个判据**：符号合并不只是「名字不一样」，它是**模型语义被改写**。
故 CC-09 增加了两条断言：① 编码在真实符号集上**单射**；② `decode(encode(s)) == s`。
单射那条是导出层唯一灾难性的失败。

### 决策四之②：优化方向反向映射错（真 bug，静默）

**现象**：CC-09 报告「目标方向 MINIMIZE != MAXIMIZE」。根因不在导出层，而在
`extract_pulp_structure` 的反向映射表：我按直觉写成 `{-1: "MINIMIZE", 1: "MAXIMIZE"}`，
而 PuLP 的常量是 **`LpMinimize = 1`、`LpMaximize = -1`**（与直觉相反，已实测确认）。

**为什么它重要**：把最大化读成最小化，会让「导出层等价性」这一判定在方向维度上恒假。
虽然此处的导出侧是对的（`to_pulp` 用的是 `pulp.LpMaximize` 符号名而非数值），但这条
判据若不比对方向，就**永远发现不了**有人把 `to_pulp` 写成 `LpMinimize`。

**修法**：改正常量表，并注明「先核实后写死」；单测里加一条回归——若 PuLP 可导入，
直接对 `pulp.LpMinimize` / `pulp.LpMaximize` 断言，避免再靠文档臆测。

## 决策五：验证在仓外进行，仓内保持零依赖

**决定**：为闭合 CC-09，在**仓外**建隔离 venv（`~/.workbuddy/binaries/python/envs/solver`，
PuLP 3.3.2 + HiGHS 1.15.1）跑一次真实求解并留证。仓库不新增依赖、不进依赖清单。

**理由**：零第三方依赖是本仓硬约束（配置用 JSON、测试用 stdlib unittest）。把 PuLP 写进
仓库依赖会让这条硬约束失效，也会让判据的可复现性依赖网络。仓外验证同时保住两者：
判据在零依赖环境**仍可判定**（SKIP 是真话），而验证本身有据可查。

**推论（写进制品）**：在零依赖环境里 `backend-check` 的 BB-07/BB-08/BB-09 与 CC-09 都是
SKIP。**SKIP 不等于通过**——在那台机器上，「后端链路没走样」仍未验证。故 BB-09 把
「装上 PuLP 后必须真的 PASS」做成判据，防止它二次挂账。

## 决策六：替换性要有实证，不是声明

**决定**：
1. BB-06 用**忽略可用性**的 `select_backend` 证明「改 `active` 即改变选中后端」；
2. AST 查「后端名不得出现在 if/elif/while 的比较里」（禁字符串没有意义——名字必须出现
   在 import 与制品里；要禁的是它**参与分支**这个动作）；
3. 注入一个制品外声明的**替身后端**，整链路（选后端 → 求解 → 状态归一 → 解回读）必须跑通。

**实证**：把 `active` 从 `pulp_highs` 改为 `pulp_cbc`（或命令行 `--prefer pulp_cbc`），
**源码零改动**，两次求解给出同一个最优值 460000.0，业务侧 C1 残差均为 0：

| 后端 | 求解器 | 秒 | 目标值 | 双侧可行性 |
|---|---|---|---|---|
| pulp_highs | HiGHS 1.15.1 | 0.004 | 460000.0 | 编译侧 ✓ / 业务侧 ✓ |
| pulp_cbc | CBC | 0.057 | 460000.0 | 编译侧 ✓ / 业务侧 ✓ |

两个独立求解器对同一模型给出一致最优值，本身也是一次跨来源对账。

**若只有一个候选**，BB-06 判 **FAIL 而非 PASS**：没有第二个候选就没有证据，
不能把「无从验证」记成「已验证」。

## 决策七：判据不得在它该拦的输入上崩

**决定**：`to_pulp` 在构造后端对象**之前**自查符号闭包，缺口时抛 `CompilerError`
（而不是让 `KeyError` 冒出来）；CC-09 把它归一到 **BLOCKED** 并带出缺口清单。
CC-09 的三条出口必须分开：

| 出口 | 状态 | 含义 |
|---|---|---|
| 构造失败（符号闭包缺口） | BLOCKED | 导出层拒绝了这份模型 |
| `to_pulp` 返回 None | SKIP | 本机没装 PuLP（附复跑条件） |
| 构造成功 | PASS / FAIL | 逐项对账 |

**理由**：CC-09 会调用 `to_pulp`，而一份 CC-03 该判 FAIL 的模型（行里引用了未声明的
符号）会让 `lpSum` 抛 `KeyError`，把整条校验以异常形态炸掉——而不是报出一条 FAIL。
判据不能在它该拦的输入上崩。若不分这三条出口，「导出层拒绝」还会被读成「本机没装」。

## 决策八：CC-12 同样适用于适配层

在 `backend.py` 中新增的编码函数里写了 `int(..., 16)`，**立刻被 CC-12 抓到**（裸数值
字面量）。按「数值必须具名」的规则提成 `SYMBOL_ESCAPE_RADIX = 16`。

这条值得记：CC-12 不是只管业务系数的形式主义——它管的是「表达式里出现了没有名字的
数值」这个**动作**。连进制也不例外。判据在自己新写的代码上生效，说明它不是在事后
合规检查，而是在参与实现。

## 决策九：输出文案里的环境断言必须由能力探测得出，不得硬编码

**现象**：`compile-check` 与 `backend-check` 的「N 条 SKIP」提示原先写死为
「（本机无 PuLP ⇒ CC-09 恒为 SKIP，须在 T04-02C 复跑）」。在**装上 PuLP 的机器**上
这句成了假话——本轮已经跑过 CC-09 并判 PASS，剩下的 SKIP 是 LP 变体 CC-08 那类
**结构性豁免**，与 PuLP 无关。

**修法**：把「本机有没有 PuLP」做成一个**具名探针** `compiler.pulp_available()`
（探测方式与 `to_pulp` 逐字相同：`import pulp`），CLI 读它决定说哪一句。探针住在
`compiler.py` 而非 CLI，是因为求解器包只许在制品声明的模块内 import（BB-03）——
CLI 自己 `import pulp` 去写文案会被（正确地）判违规。探针与导出层**不得给出不同
答案**，故加一条单测断言 `pulp_available() == (to_pulp(model) is not None)`。

**为什么重要**：这与**决策二**是同一条根因。`SKIP ≠ PASS` 是**永远为真**的断言；
「本机无 PuLP」只是一个**当时为真的猜测**，环境一变就成了假话。台账可以如实写
「没检查」，但不能替环境断言一项它其实具备的能力。

**顺带纠正的一处同类问题（测试侧）**：`test_lp_compiler.TestCheckLayerGreen` 原先
断言 `CC-09 == "SKIP"`，只在零依赖机器上成立。测试不得假定本机没装 PuLP，改为按
`import pulp` 探测取值——**缺能力时假 PASS 与有能力时假 SKIP 同属回归，两个方向都要拦**。

## 后果

**已闭合**：T04-02B 的 CC-09 挂账；「导出层没走样」首次被真实验证过（并据此修出两处
静默走样）。

**新增的能力边界**：

- 后端的选择、能力矩阵、状态映射、审计基准全部住 `config/solver_backend_spec.json`；
- 加一个后端 = 在制品里注册一条目 + 在 `ADAPTERS` 里放一个实现体，业务侧零改动；
- 能力不足、条目未实现、环境缺失三种「跑不了」在状态域里互不顶替。

**已知挂账**：

1. `highspy_direct` 已声明未实现（选到判 UNSUPPORTED）。「能力矩阵完整」≠「后端已就绪」。
2. PuLP 的 `Undefined` 归一为 AMBIGUOUS 是**推理**而非实测枚举；实测探针只覆盖
   Optimal / Infeasible / Unbounded 三格。
3. **上游漂移**（本轮实测）：
   - `PULP_CBC_CMD` 已弃用（4.0 移除）⇒ `pulp_cbc` 是随版本失效的候选，升级时须同步改
     制品，否则 BB-06 会退化为「只有一个候选」而 FAIL（该 FAIL 是真的）。
   - `LpVariable(name, ...)` 直接构造与 `prob.constraints` 的字典用法 4.0 将变 ⇒ 受影响的是
     T04-02B 的导出层。CC-09 的接口面已刻意压到最小，就是为了让这次迁移的影响面可枚举。
4. BB-07 的目标值重合容差（1e-6 + 1e-6·|Z|）对成交价量级相当于 0.1~10 元。若某后端
   的表示误差更大，应**按后端分别声明**容差，而不是全局放宽——放宽到能容忍错值就不再是判据。
5. BB-03 的求解器包名单是白名单，拦不住「用一个没列进名单的求解包」。
