## 逐项维度深度诊断与改进方案

### 1. 视觉层级 (Visual Hierarchy)

**合理程度判断**：**中等**。页面采用经典的“左侧控制舱 (390px) + 右侧决策沙盘”双栏结构，符合工程测算类复杂生产力工具的心智模式；但首屏视线引导分散，状态层级定义不清。

**具体问题与界面现象**：

* **双主 CTA 冲突**：右侧准备面板中的 `#calculateBtn`（`btn-primary`，“识别文件并计算”）与视口底部常驻浮动操作坞中的 `#dockCalcBtn`（`dock-btn primary`，“一键重新推演”）在未计算阶段同时高光呈现，抢夺用户的首要行动点。
* **右侧主舞台状态混乱**：在未测算前，界面同时展示了 `#preparePanel`（就绪检查面板）、空的 4 联 KPI 看板（数值全为破折号 `—`）以及空表头。尚未就绪的信息与结果骨架混排，造成界面噪声过大。
* **左侧表单信息密度过载**：从项目关联、目标报价、比率滑块、成本税抵扣明细表再到双文件上传，所有卡片全部平铺展开，纵向滚动过长，缺乏“基础必填”与“高级调参”的折叠节奏。

**优化方向与可落地方案**：

* **统一操作主入口**：将计算行动点收敛至悬浮 Dock，`#preparePanel` 内部改为只读的阶段指示，仅在所有前置检查项全部勾选变绿后，高亮触发主 CTA。
* **实施阶段化状态机渲染**：
* *未导入期*：右侧主舞台仅展示“资料解析与推演准备看板”，收起 KPI 与表格；
* *推演完成期*：就绪面板自动收折为顶部紧凑状态胶囊（Status Bar），完整展开 KPI、决策图表与子目表。


* **左栏模块分组折叠**：将“成本进项税抵扣模型”和“风控防畸形高级阈值”包装为默认收起的折叠抽屉（Accordion），聚焦首要目标总价与清单导入。

### 2. 色彩体系 (Color System)

**合理程度判断**：**较弱**。设计初衷采用“宋代暖纸质感（`--page-bg: #f4f3f0`）+ 墨石灰（`--accent: #2f2e2b`）+ 矿物点缀色”，理念优雅；但在具体组件实现中，混入了完全冲突的现代高饱和科技蓝与土豪金，造成严重的色彩污染。

**具体问题与界面现象**：

* **外来色彩污染**：在 `styles.css` 中，`.cs-opt:hover` 居然硬编码使用了 `rgba(10, 96, 208, .08)`，`.cs-opt.cs-selected` 使用了 `rgba(10, 96, 208, .14)`。这种 macOS/iOS 风格的高饱和亮蓝色（`#0a60d8`）与底层的暖纸灰黄色底色（`#f4f3f0`）产生强烈的冷暖色调对冲，脏感明显。
* **侧边栏品牌字土豪金质感脱节**：`.brand-text strong` 设置为 `color: #e6b96a; text-shadow: 0 1px 3px rgba(0,0,0,.35)`，偏向传统重度装饰质感，与扁平干练的现代工程 SaaS 调性不搭。
* **语义色与装饰色功能混淆**：`--module-4`（`#b5715a`，陶土橙红）在方案卡片中被用作正常方案的标记徽章（`.plan-card-badge`），但同时又被用于危险删除操作（`.plan-card-del:hover`）和确认弹窗警示（`.ui-confirm-title`），让用户产生“方案 A 是一个错误/危险项”的心理误判。

**优化方向与可落地方案**：

* **剔除所有硬编码冷色系**：重构下拉选中态与悬浮态色彩映射，统一使用基于主品牌的半透明叠色：
```css
/* 替换前: rgba(10,96,208,.08) */
.cs-opt:hover {
  background: color-mix(in srgb, var(--accent) 6%, transparent);
}
.cs-opt.cs-selected {
  background: color-mix(in srgb, var(--accent) 12%, transparent);
  color: var(--accent);
}

```


* **规范侧栏品牌字**：移除暗黑文字阴影，将金黄色调降至低饱和哑光米金，或回归高对比度冷白文字。
* **语义色解耦**：将业务模块色（Mineral Colors）与系统反馈色（Success/Warn/Danger）严格区分。危险删除固定绑定 `--danger: #c25d4f`，方案徽章使用中性深灰或专属的方案标识色。

### 3. 字体排印 (Typography)

**合理程度判断**：**良好**。选用了现代工程界面表现出色的 `MiSans VF` 字体，且在数字展示区域全量声明了 `tabular-nums`，整体可读性扎实；但在字重层级和微观数据排版上缺乏严格的阶梯规范。

**具体问题与界面现象**：

* **字重声明极其混乱且碎片化**：样式表中充斥着大量随意的细分字重：`font-weight: 750`（标题）、`650`（副标题）、`480`（元数据）、`780`（弹窗）。虽然 VF（Variable Font）支持任意字重插值，但在不支持该字体切片或降级到标准系统字体（微软雅黑 / PingFang SC）时，浏览器会粗暴地将其阶梯化为 400 或 700，导致非预期的排版溢出与字符跳动。
* **微字号跌破安全阈值**：`.nav-group-title` 设置为 `10.5px`，`.version-line` 和部分说明为 `11px` / `11.5px`。在 Windows 操作系统（96 DPI 屏幕）下，中文字符小于 12px 会出现明显的边缘笔画糊化。
* **数值与货币符未对齐基线**：如 `.input-prefix`、`#kpiTotalVal` 与单位的比例关系没有系统定义，前缀货币符号与主数值等大，喧宾夺主。

**优化方向与可落地方案**：

* **严格收敛字重至四大标准档位**：
* `Regular (400)`：正文、说明文字、常规表格数据；
* `Medium (500)`：输入框内容、表头、辅导航文字；
* `SemiBold (600)`：子目名称、按钮文本、KPI 标签；
* `Bold (700)`：卡片主标题、页面大标题、核心 KPI 巨型数值。


* **确立 12px 最小字号红线**：分组标题统一设为 `12px`，配合 `letter-spacing: 0.05em` 与 `text-transform: uppercase` 提升高级感。
* **数据排印微观比例规范**：
```css
.kpi-val {
  font-size: 28px;
  font-weight: 700;
  letter-spacing: -0.02em;
}
.kpi-unit, .input-prefix {
  font-size: 0.65em; /* 保持与数值同比例缩放 */
  font-weight: 500;
  color: var(--text-secondary);
  margin-right: 2px;
}

```

### 4. 间距与栅格 (Spacing & Grid Layout)

**合理程度判断**：**偏弱**。界面没有建立基于 4px 或 8px 的间距系统（Spacing System），组件内边距与外边距随手书写现象明显，整体视觉节奏感欠佳。

**具体问题与界面现象**：

* **非规范的奇数间距散落**：
* `.brand`：`padding: 22px 20px 18px`
* `.main-content`：`padding: 26px 34px 52px`
* `.param-grid`：`gap: 18px`
* `.card-head`：`margin-bottom: 14px`
* 大量出现 7px、9px、11px、13px、14px 等随机间距，元素之间未能形成规律的呼吸节奏。


* **横向排布缺乏约束**：`.main-content` 设为了 `max-width: none`，在 2K/4K 超宽带显示器下，右侧表格会无限横向拉伸，导致项目编码与建议单价之间横向间距过长，视线扫读极其疲劳。

**优化方向与可落地方案**：

* **定义标准 8-Point Spacing Tokens**：
```css
:root {
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --space-4: 16px;
  --space-5: 20px;
  --space-6: 24px;
  --space-8: 32px;
  --space-10: 40px;
}

```


* **限制内容区最大宽度与栅格比例**：为 `.main-content` 增加 `max-width: 1680px; margin: 0 auto;`。左栏锁定为 `380px`，右栏设为 `1fr` 弹性填充，确保高分辨率下的紧凑感与视线聚焦。

### 5. 组件视觉风格 (Component Styling & Aesthetics)

**合理程度判断**：**较弱**。核心问题在于“风格人格分裂”。一个原本采用纸质墨水风格的后台，局部组件却突兀使用了拟物化玻璃质感。

**具体问题与界面现象**：

* **拟物毛玻璃与扁平纸面的对撞**：查看 `.plan-select` 与 `.cs-trigger`，代码中使用了：
```css
border: 1px solid rgba(255,255,255,.85);
background-color: rgba(245,247,251,.60);
backdrop-filter: blur(16px) saturate(1.5);
box-shadow: 0 1px 2px rgba(0,0,0,.06), 0 6px 18px rgba(0,0,0,.07), inset 0 1px 0 rgba(255,255,255,.90);

```


这是典型的 iOS 拟物毛玻璃高光风格，而周围的输入框（`.field input`）是极为纯净的扁平暖白底框，两者并排摆放如同拼接两个不同系统的页面截图。
* **Tooltip 突兀黑盒**：`.field[data-tip]::after` 突然变成了黑灰色高斯模糊容器（`background: linear-gradient(..., rgba(30,32,38,.62))`），带有强烈的电竞/深色模式质感，在浅色温暖的底色上像一块破损的补丁。
* **控件圆角层级倒挂**：
* 卡片圆角：`16px`；
* 单行普通输入框：居然使用了 `--radius-tile: 12px`；
* 单行输入框在 32px~36px 高度下配置 12px 圆角会导致左右两侧几乎形成半圆胶囊，形态松散无力，不像严肃的算量工具，反倒像消费级即时聊天应用的对话框。



**优化方向与可落地方案**：

* **剔除拟态玻璃效果，回归精致实体质感**：移除所有 `backdrop-filter` 与 `inset 0 1px 0` 白边高光，下拉框外观与输入框严格对齐：
```css
.cs-trigger, .plan-select {
  background-color: var(--surface-card);
  border: 1px solid var(--border-input);
  box-shadow: 0 1px 2px rgba(35,34,32,0.03);
  backdrop-filter: none;
  border-radius: var(--radius-control); /* 统一为 8px */
}

```


* **重塑气泡提示（Tooltip）**：改用温和的墨灰哑光实体背景，移除多层模糊渐变，边框使用低反差灰色。
* **重整圆角阶梯（Radius Hierarchy）**：
* 控件级（Input/Select/Button）：`6px ~ 8px`；
* 组件单元级（Sub-card/Table block）：`10px`；
* 容器级（Card/Modal）：`12px ~ 14px`；
* 胶囊专用（Pill/Badge）：`999px`。

### 6. 交互动效 (Micro-interactions & Animation)

**合理程度判断**：**一般**。全局大部分动效仅简单堆叠了 `transition: ... .15s`，缺乏工程级物理缓动曲线与状态微动效。

**具体问题与界面现象**：

* **大面积容器 Card 上浮引发眩光与抖动**：
`.card:hover { box-shadow: var(--shadow-overlay); }`。
当用户在左侧参数栏填写表单时，鼠标掠过大卡片，整块占屏幕 30% 面积的区域频繁产生大面积深度阴影扩散。对于非点击性质的内容容器，这种过度的反馈给用户造成“整张卡片可以拖拽或被点击”的错误心理暗示。
* **模态弹窗缺乏进出场物理重量**：`.modal-mask` 的动画仅有最基础的 `@keyframes fadeIn { from{opacity:0} }`，弹窗本身瞬间呈现，缺乏弹性缩放与位移。

**优化方向与可落地方案**：

* **取消非可交互大容器的全局 Hover 阴影**：卡片应作为沉稳的“承载面”（Base Surface），仅当元素作为实体按钮、文件上传拖拽框、或方案选择长卡片（`.plan-card`）时，才触发 Hover 抬升反馈。
* **建立统一的贝塞尔缓动库**：
```css
:root {
  --ease-out-cubic: cubic-bezier(0.215, 0.61, 0.355, 1);
  --ease-spring: cubic-bezier(0.175, 0.885, 0.32, 1.15);
  --dur-fast: 160ms;
  --dur-normal: 240ms;
}
.modal {
  animation: modalEnter var(--dur-normal) var(--ease-spring);
}
@keyframes modalEnter {
  from { opacity: 0; transform: scale(0.96) translateY(12px); }
  to { opacity: 1; transform: scale(1) translateY(0); }
}

```

### 7. 交互逻辑 (Interaction Logic)

**合理程度判断**：**中等**。核心业务逻辑闭环完整，但在控件物理操作和状态容错上存在硬性逻辑缺陷。

**具体问题与界面现象**：

* **双原生 Range 滑块重叠碰撞死锁**：
在 `.guardrail-track` 内部，通过绝对定位直接叠放了两个原生 `<input type="range">`（`#ratioLow` 与 `#ratioHigh`）。在原生浏览器渲染机制下，上面的滑块会永久阻断下面滑块的点击判定；当两个滑块的值重叠（例如都在 50%）时，用户将完全无法拖动被盖在下层的滑块。此外，两个滑块未做交叉阻止，极易出现 `ratioLow > ratioHigh` 的逻辑悖论。
* **就绪状态（Preparation Checklist）与即时反馈脱节**：
`#preparePanel` 中的状态圆点默认静态标为 `data-state="pending"`。当用户在左侧选择完项目或上传文件后，检查清单中的点缺乏动态成功动画或提示引导，没有明确让用户感知到操作的闭环进展。

**优化方向与可落地方案**：

* **重构双滑块控制交互（Dual-handle Slider）**：
* 改用统一的自定义 Slider 控件，通过外层单一轨道监听鼠标拖拽事件，或者在原生方案下动态切换重叠滑块的 `z-index`（依据鼠标位置靠近哪一个 handle 来动态提权）；
* 在 JavaScript 中注入碰撞锁：`ratioLow.value = Math.min(this.value, ratioHigh.value - 5)`，确保安全防线区间物理合法。


* **输入完成度即时响应链路**：表单监听 `input` 与 `change` 事件，当“目标报价”与“清单上传”达成条件，检查清单项立刻执行打勾微动效（变绿 + 弹跳反馈），当且仅当 3 项满足，右下角推演按钮产生一次微弱呼吸光晕，完成视线接力。

### 8. 交互体验 (UX / Usability)

**合理程度判断**：**一般**。在复杂工程造价场景下，部分细节对日常高频使用的造价工程师不够友好。

**具体问题与界面现象**：

* **常驻悬浮操作坞（Floating Dock）对表格数据遮挡**：
`.floating-dock` 采用 `position: fixed; bottom: ...` 居中悬浮在视口下方。而下方的 `.table-scroll` 包含了多达 10 列的清单表格。当用户滚动到表格最后几行查看“合计/税后汇总”或操作末尾行时，底部的 3 个悬浮按钮正好挡住了表格最核心的汇总行，且表格底部没有预留安全外边距。
* **KPI 穿透后表格状态丢失认知**：
界面提示“💡 点击 KPI 卡片可穿透联动表格”，但点击毛利或风险 KPI 后，卡片本身缺少一个明确的“持续激活状态”（如轮廓光、微小指示三角或下压凹陷态），用户在查看表格时极易忘记当前处于局部过滤状态，误以为项目只有这几条清单。
* **上传区域缺少即时预览摘要**：
上传成功后仅展示了一个文件名，对于动辄几千项的工程清单，缺乏诸如“已解析 342 条子目 / 发现 3 条未匹配项”的关键即时摘要凭证，无法给予预算员确定性安全感。

**优化方向与可落地方案**：

* **增加页面底部安全操作保护区（Safe Area）**：
给 `.main-content` 或 `.table-section` 底部增加至少 `88px` 的 `padding-bottom`，确保即便表格滚动到最底部，最后一行也能完整显露在浮动 Dock 上方。
* **为 KPI 卡片增加 Active 穿透激活态**：
```css
.kpi-card.is-active {
  border-color: var(--accent);
  box-shadow: 0 0 0 2px var(--accent), var(--shadow-overlay);
  background: var(--surface-card);
}
.kpi-card.is-active::after {
  content: "";
  position: absolute;
  bottom: -6px; left: 50%; transform: translateX(-50%);
  border-width: 6px 6px 0; border-style: solid;
  border-color: var(--accent) transparent transparent;
}

```


同时在表格工具栏的 `.filter-chips` 旁动态显示一个醒目的清空筛选徽标（`清除 KPI 穿透 ✕`）。

### 9. 整体视觉一致性 (Overall Visual Consistency)

**合理程度判断**：**较弱**。侧边栏与主工作区的明暗反差过于生硬，且界面内部描边与阴影规范存在多重标准。

**具体问题与界面现象**：

* **左右极端明暗割裂**：
侧边栏采用沉浸深黑背景（`--drawer-bg: #232220` 到 `#2d2c29`），而主工作区是极浅的暖纸白（`#f4f3f0`）。由于侧边栏宽度高达 `258px`，在用户的视野左侧形成了一块巨大的纯黑暗区。这在深色模式下很协调，但在明亮的日间暖纸风格中，深黑侧栏显得厚重笨拙，产生了强烈的界面割裂感。
* **分割线与边框线标准不一**：
页面中同时混用了：
1. 常规实线：`1px solid var(--border)`（`#ecebe5`）；
2. 深色输入线：`1px solid var(--border-input)`（`#e0ded6`）；
3. 虚线上传框：`1.5px dashed var(--border-input)`；
4. 白透明亮线：`1px solid rgba(255,255,255,.85)`（下拉框）。
四种边框在不到 300px 的纵向空间内交织，破坏了界面整体的工整感与平整度。



**优化方向与可落地方案**：

* **侧边栏轻量化或色彩调和**：
将侧边栏背景调整为与纸质风格同一色系的微深色，或者直接采用与主背景同色系的半透明亚光白底（如在工作台模式下采用浅色极简侧栏，仅在特定专业大屏监控时切入黑底），弱化生硬的明暗切割：
```css
/* 推荐的轻质工程灰侧栏 */
.sidebar {
  background: #eae8e1;
  border-right: 1px solid var(--border);
  color: var(--text);
}
.sidebar .nav-item {
  color: var(--text-secondary);
}
.sidebar .nav-item.active {
  background: var(--surface-card);
  color: var(--text);
  box-shadow: 0 1px 3px rgba(35,34,32,0.06);
}

```


* **统一步进边框系统**：废止所有基于半透明纯白的边框代码，容器与组件全部收敛于 `--border`（基底划分）与 `--border-input`（交互控件划分）两级。
